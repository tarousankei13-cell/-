## 1. 結論

### ✅ Discord 上での注文組み立ては **実現可能**。しかも **hex を経由する必要がない。**

hex は「ブラウザで組んだ注文を利用者へ渡す」ための中間形式にすぎない。
BOT がサーバー側で注文を組めるなら、**hex を作らずそのまま `StoreOrder` を呼べばよい。**

```
【現行】利用者 → mcdon.asia でカート作成 → hex をコピー → Discord に貼る → BOT が決済
【将来】利用者 → Discord でカート作成 ───────────────────────▶ BOT が直接 StoreOrder
                                                              （hex 不要・mcdon.asia 不要）
```

必要な材料は**すべて揃った**。

| 必要なもの | 状態 | 出所 |
|---|---|---|
| protobuf スキーマ | ✅ 完全取得 | `docs/07` §4 |
| 商品コード・商品名 | ✅ **214商品 100%** | 本レポート |
| 価格（店内/持帰/デリバリー別） | ✅ 取得 | 本レポート |

## 3. 商品データモデル

### 3.1 `products[productCode]`

```jsonc
{
  "productCode": "9206",
  "productClass": "VALUE_MEAL",        // PRODUCT（単品） / VALUE_MEAL（セット）
  "dayPart": "DAY_MENU",               // DAY_MENU / 朝マック等
  "priceList": [
    {"priceCode": "EATIN",   "price": 290},   // 店内
    {"priceCode": "TAKEOUT", "price": 290},   // 持ち帰り
    {"priceCode": "OTHER",   "price": 440}    // デリバリー
  ],
  "price":         {"valid": true, "price": 290},
  "deliveryPrice": {"valid": true, "price": 440},
  "composition":    [ ... ],   // 固定の構成品（必ず入る）
  "choices":        [ ... ],   // 選択項目（サイド・ドリンクなど）
  "canAdds":        [ ... ],   // 追加できるトッピング
  "autoCondiments": [ ... ],   // 自動で付く調味料
  "comments":       [ ... ]    // 「ピクルス抜き」等の指定
}
```

> ⚠️ **受取方法で価格が変わる**（`EATIN` / `TAKEOUT` / `OTHER`）。
> 負担率の計算は**利用者が選んだ受取方法の価格**を定価として行うこと（`docs/04` §3.3）。

### 3.2 構成要素（`composition` / `choices` / `canAdds` 共通）

```jsonc
{
  "productCode": "9987009",      // この枠の識別子
  "referenceProduct": "2020",    // 参照商品
  "defaultProduct":   "2020",    // 既定の選択（例: ポテトM）
  "defaultQuantity": 1,
  "minQuantity": 1,              // 0 なら省略可能
  "maxQuantity": 1,
  "priceList": [],               // 差額（例: Lサイズは +50円）
  "costInclusive": true          // セット価格に含まれるか
}
```

→ Discord UI では `choices` を Select、`canAdds` をトグルボタンとして出せばよい。

### 3.3 商品名の取得 ✅ カバー率 100%

`products` 自体に名前は無いが、`sizeVariants` / `collections` / `relatedSets` など
他セクションの `tName: {"en": ..., "ja": ...}` を**再帰的に収集**すると、
**214商品すべての日本語名が復元できる**（実測で欠落 0 件）。

```python
def harvest_names(node, out):
    """menu.json 全体を再帰的に走査して productCode → 日本語名 を集める"""
    if isinstance(node, dict):
        pc, tn = node.get("productCode"), node.get("tName")
        if pc and isinstance(tn, dict) and tn.get("ja"):
            out[str(pc)] = tn["ja"]
        for v in node.values():
            harvest_names(v, out)
    elif isinstance(node, list):
        for v in node:
            harvest_names(v, out)
```

実測例:

| `1940` | 倍マックポーク | ¥380 |
| `2110` | ホットアップルパイ | ¥140 |

| `9206` | チキンフィレオ® セット | ¥290 |

## 5. 唯一の未確定点 — `shortOrderCode`

`Order.shortOrderCode`（field 2）はサーバーが払い出す値と推定される。
HATTIMCD の `_build_store_order_body` では**条件付き**で、空でも body を組める。

```python
if short_order_code:
    inner += _pb_str(2, short_order_code)   # ← 省略可能な実装になっている
```

### 検証手順（Phase 5 で実施）

1. `shortOrderCode` を省略した body で `StoreOrder` を実行する
2. 成功すれば → **サーバー払い出し。BOT 側で生成不要**
3. 失敗すれば → `CreateOrder` を先に呼んで払い出しを受ける経路を実装する

**少額の商品1点で検証すること。**

## 7. 【追記】新商品の自動反映と時間帯制御

### 7.1 新商品・終売・価格改定への自動追従

`menu.json` は**マクドナルド側が更新する**ため、定期的に取り込めば新商品は自動で入る。

| タイミング | 対象 | 備考 |
|---|---|---|
| **BOT 起動時** | 登録済みの全店舗 | 起動直後から最新 |
| **6時間ごと**（既定） | 直近30日に注文のあった店舗 | 間隔は `/config menu interval` で変更可 |
| **注文の直前** | その店舗のキャッシュが**30分以上古い**場合のみ | 価格ズレを防ぐ最後の砦 |
| **`/menu sync <店舗ID>`** | 指定店舗 | 手動で即時更新 |

```python
async def sync_menu(store_id: str) -> MenuDiff:
    store = await fetch_store(store_id)                  # {storeId}.json
    cat   = store["store"]["api"]["catRootUrl"]          # ★groupの総当たり不要
    menu  = await fetch_json(f"{cat}/{store_id}/menu.json")
    names = harvest_names(menu)                          # §3.3
    return await upsert_products(store_id, menu, names)  # 差分を返す
```

### 7.2 差分の通知

同期で差分が出たら**管理者チャンネルへ自動投稿**する。運営が値上げや新商品に気づける。


### 7.3 時間帯による商品の出し分け ✅ 完全対応可能

取得済みデータだけで、**商品単位の提供時間まで**制御できる。

#### ① 商品の `dayPart`（実測 247商品の内訳）

| 値 | 件数 | 意味 |
|---|---|---|
| `DAY_MENU` | 86 | 通常メニュー |
| `BREAKFAST_DAY_MENU` | 46 | 朝・通常どちらでも |
| `BREAKFAST_MENU` | 35 | 朝マック限定 |
| （空） | 80 | 構成品・オプション類 |

#### ② 店舗の時間帯定義（`{storeId}.json` → `mopDaypartAbilityLists`）

実測値（南砂町店）— 分は 0時からの経過分:

| daypart | 表示 | 注文可能 |
|---|---|---|
| `DAYPART_BREAKFAST` | 05:50–10:20 | **06:00–10:20** |
| `DAYPART_REGULAR` | 10:20–23:50 | **10:20–23:50** |
| `DAYPART_BREAKFAST_REGULAR` | 05:50–23:50 | 06:00–23:50 |
| `DAYPART_HIRU_MAC` | 10:20–23:50 | **10:20–14:00** |
| `DAYPART_YORU_MAC` | 10:20–23:50 | **17:00–23:50** |

→ ヒルマック・夜マックの時間帯まで正確に取れる。

#### ③ ★ `limitedAbility` — 商品コード単位の提供時間

`menu.json` の `limitedAbility` には、**日付 × 商品コードごと**に
`visible` / `checkoutable` / `checkinable` の時間帯が入っている。

```jsonc
"limitedAbility": {
  "<日付>": { "ability": {
    "1010": { "productCode": "1010",
              "visible":      [{"start": 620, "end": 1430}],
              "checkoutable": [{"start": 620, "end": 1430}],
              "checkinable":  [{"start": 630, "end": 1430}] },
    ...
  }}
}
```

**これが時間帯制御の決定版。** 商品ごとに個別の提供時間が定義されている。

#### 実装ルール

```python
def is_orderable(product_code: str, now: datetime, store: Store) -> bool:
    """注文時刻に、その商品が注文可能かを判定する"""
    minutes = now.hour * 60 + now.minute
    # ① limitedAbility に個別定義があれば最優先
    if (win := store.limited_ability.get(today()).get(product_code)):
        return any(w["start"] <= minutes < w["end"] for w in win["checkoutable"])
    # ② 無ければ dayPart と店舗の daypart 時間帯で判定
    return matches_daypart(product_code, minutes, store)
```

- **`checkoutable` で判定する**（`visible` は「表示されるが注文は不可」の時間帯を含む）
- 一覧では時間外の商品を**そもそも出さない**
- カート投入後に時間帯を跨いだ場合に備え、**確定の直前に再判定**する
  → 時間外なら「⚠️ 販売時間が終了しました」と表示して確定を止める
