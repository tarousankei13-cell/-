| ID | 決定事項 |
|----|---------|

| R-12 | **トークンとオーナーIDは `main.py` に直書き**。その他の設定はすべてコマンドで行う |

### 3.2 複式元帳（★中核）

残高カラムを直接 UPDATE する設計は必ず壊れる。**残高は元帳の集計として導出する。**

```sql
CREATE TABLE ledger (
  id         BIGSERIAL PRIMARY KEY,
  tx_id      UUID   NOT NULL,
  account    TEXT   NOT NULL,
  amount     BIGINT NOT NULL,     -- 正=増 / 負=減
  kind       TEXT   NOT NULL,     -- charge/hold/release/capture/subsidy/adjust
  order_id   UUID,
  receipt_id UUID,
  memo       TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_ledger_account ON ledger(account);
CREATE INDEX idx_ledger_tx      ON ledger(tx_id);

CREATE VIEW balances AS
  SELECT account, SUM(amount) AS balance FROM ledger GROUP BY account;
```

**勘定科目**

| 勘定 | 意味 |
|------|------|
| `issuance` | 系の外から入ってきた金（チャージの相手勘定） |
| `user:<discord_id>` | 利用者の利用可能残高 |
| `user:<discord_id>:hold` | 注文処理中のホールド |
| `subsidy_pool` | 管理者負担のプール |
| `settlement` | マクドナルドへ支払った累計 |

**不変条件**: 任意の `tx_id` について `SUM(amount) = 0`。毎時チェックする。

**取引パターン**

| 種別 | 仕訳 |
|------|------|
| チャージ ¥1,000 | `issuance` −1000 / `user:X` +1000 |
| ホールド ¥354 | `user:X` −354 / `user:X:hold` +354 |
| 解放（失敗時） | `user:X:hold` −354 / `user:X` +354 |
| 確定（成功時） | `user:X:hold` −354 / `settlement` +354 |
| 負担 ¥236 | `subsidy_pool` −236 / `settlement` +236 |

> 定価 ¥590 = 利用者 ¥354 + 負担 ¥236 が `settlement` に積み上がり、常に整合する。

**残高取得は必ずこの形で**（マイナス残高を構造的に防ぐ）:

```sql
SELECT COALESCE(SUM(amount), 0) FROM ledger
 WHERE account = 'user:123' FOR UPDATE;   -- advisory lock と併用
```

### 3.3 負担率ルール

```sql
CREATE TABLE subsidy_rules (
  id           SERIAL PRIMARY KEY,
  scope        TEXT   NOT NULL,        -- 'user' | 'role' | 'global'
  target_id    BIGINT,                 -- discord user_id / role_id / NULL
  subsidy_rate NUMERIC(5,2) NOT NULL,  -- ★管理者負担率(%)  例 40.00
  priority     INT    NOT NULL,        -- 小さいほど優先
  monthly_cap  BIGINT,                 -- 月間負担上限(円) NULL=無制限
  enabled      BOOLEAN NOT NULL DEFAULT TRUE,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**解決アルゴリズム**（`core/subsidy.py`）

```
1. scope='user'   かつ target_id = 利用者   → あれば即採用
2. scope='role'   かつ 利用者が保持するロール → 複数該当時は priority 最小、
                                                 同値なら subsidy_rate 最大を採用
3. scope='global'                            → 既定値
4. 月間負担上限に達している場合は global にフォールバックし、パネルに理由を明示
```

**金額計算（R-6: 切り上げ）**

```python
user_amount    = math.ceil(list_price * (100 - subsidy_rate) / 100)
subsidy_amount = list_price - user_amount
# 検算: 590 × (100-40)/100 = 354.0 → 354 ✅（添付画像と一致）
```

## 4. 注文 Saga（★最重要）

`StoreOrder` → `AuthoriseOrder` → `GetPaidOrder` は別リクエストで、間で必ず落ちうる。

```
CREATED
  └▶ QUOTED           hex解析・受取方法選択・料率解決 完了（まだ金は動かない）
       └▶ BALANCE_HELD    ledger: user → user:hold
            └▶ ACCOUNT_LOCKED  MCDアカウントを確保（他注文と排他）
                 └▶ MCD_STORED     StoreOrder 成功 → order_token 取得
                      └▶ MCD_AUTHORISED  AuthoriseOrder 成功 ⚠️ ここから自動返金禁止
                           └▶ RECEIPT_FETCHED  receipt_number 取得
                                └▶ CAPTURED   ledger: hold → settlement / subsidy → settlement
                                     └▶ NOTIFIED   DM送信 + 実績チャンネル送信
                                          └▶ COMPLETED

失敗時:
  QUOTED / BALANCE_HELD / ACCOUNT_LOCKED / MCD_STORED で失敗
      → COMPENSATING → ホールド解放 → REFUNDED（利用者に全額戻る）
  MCD_AUTHORISED 以降で失敗
      → MANUAL_REVIEW ⚠️ 自動返金しない。管理者チャンネルへ承認ボタン付きで通知
```

### 4.1 鉄則

1. **状態遷移は必ず DB に同期コミットしてから次の処理へ進む。** メモリ上の状態を信用しない。
2. **`MCD_AUTHORISED` 到達後は絶対に自動返金しない。** 実際に課金されている可能性がある。
3. **起動時リカバリ**: `COMPLETED` / `REFUNDED` / `MANUAL_REVIEW` 以外の注文を全件洗い出し、
   - `MCD_STORED` → `GetPaidOrder(order_token)` で結果を確認して前進または補償
   - `MCD_AUTHORISED` → `GetPaidOrder` で `receipt_number` を復元して前進
   - それ以前 → 補償してホールド解放
4. **冪等性**: 確定ボタンに `idempotency_key` を埋め、UNIQUE 制約で弾く。
   2回目以降は**既存注文の状態を返すだけ**。
5. **同時実行制御**: `pg_advisory_xact_lock(hashtext('order:' || discord_id))` で
   1利用者あたり同時1注文に制限。

### 4.2 リトライ方針

| 段階 | リトライ | 理由 |
|------|---------|------|
| トークン取得 / `GetPosIdToken` | 最大2回（指数バックオフ） | 冪等 |
| `StoreOrder` | group を変えて総当たり（`docs/01` §4.3） | 冪等でない可能性 → **同一 group での再試行は禁止** |
| `AuthoriseOrder` | **リトライ禁止** ⚠️ | 二重課金のリスク。失敗＝ `GetPaidOrder` で状態確認へ |
| `GetPaidOrder` | 最大5回（1秒間隔） | 冪等・読み取り専用 |

## 5. サービス層の設計

### 5.1 同期I/Oの隔離（★必須）

HATTIMCD も Kyasher も `requests` ベースの完全同期ライブラリ。
discord.py（asyncio）から直接呼ぶと、**処理中の数〜十数秒 BOT 全体が固まる。**

```python
# services/mcd/client.py
class AsyncMCD:
    def __init__(self, account: MCDAccount):
        self._mcd = MCD(tokens=..., proxy=account.proxy_url)
        self._patch_fingerprint(account)   # ★docs/01 §7
        self._sem = asyncio.Semaphore(1)   # 1インスタンスに同時1リクエスト

    async def _call(self, fn, *a, **kw):
        async with self._sem:
            return await asyncio.to_thread(fn, *a, **kw)

    async def pay_from_hex(self, hex_str, card_id=None):
        return await self._call(self._mcd.pay_from_hex, hex_str, card_id)
```

**フィンガープリント注入**（`docs/01` §7 — 全アカウント共通のハードコードを解消）

```python
def _patch_fingerprint(self, acc):
    h = self._mcd._sess.headers
    h["x-vmob-uid"]              = str(acc.device_uid).upper()
    h["x-wmop-deviceid"]         = str(acc.wmop_device_id).upper()
    h["x-fb-instance-id"]        = acc.fb_instance_id
    h["x-vmob-location_latitude"]  = f"{acc.home_lat}"
    h["x-vmob-location_longitude"] = f"{acc.home_lng}"
```

> 値は**アカウント作成時に一度だけ生成して固定**する。毎回ランダムにすると逆に不自然。
> 座標は注文店舗の近傍に微小ノイズを乗せて生成するとさらに自然になる。

### 5.2 TokenVault

現状の HATTIMCD は API 呼び出しのたびに access_token と root_paseto を再取得する
（1注文で無駄な往復8回以上）。これをキャッシュ化する。

- `mcd_tokens` に暗号化して永続化。`access_exp` / `root_exp` で管理
- **期限60秒前にプロアクティブ更新**。401 受信時のみ強制再取得して1回だけリトライ
- バックグラウンドタスクで全 ACTIVE アカウントを **45分ごとにウォーム**
- ⚠️ **`refresh_token` はリフレッシュのたびにローテーションする**（`docs/01` §2-A）。
  取得した新トークンを**同一トランザクションで即 DB 保存**すること。
  保存に失敗するとそのアカウントは恒久的にログイン不能になる。

### 5.3 投機的先読み（体感速度の要）

利用者が hex を投入してプレビューパネルが開いた瞬間、**確定ボタンが押される前に**
バックグラウンドで以下を走らせる。

```
decode_hex                     （ローカル・即時）
store_group_cache から group 解決（無ければ data.cat で特定して登録）
get_store_name                 （店名表示にも使う）
MCDアカウント選択 + トークンウォーム
get_pos_paseto(該当group)      （先に取得しておく）
```

確定押下後に残るのは `StoreOrder` → `AuthoriseOrder` → `GetPaidOrder` の3往復のみ。
**「押した瞬間に終わる」体験**になる。先読み結果は 90 秒で失効させる。

### 5.4 hexutil（受取方法の差し替えとラウンドトリップ検証）

```python
async def prepare_order(hex_str: str, pickup: PickupMethod) -> PreparedOrder:
    decoded = decode_hex(hex_str)                      # docs/01 §3
    validate(decoded)                                  # store_id / amount > 0 / products 非空
    pickup_payload = PICKUP_PAYLOADS[pickup]           # docs/01 §11 ★V-1 で要確定
    return PreparedOrder(decoded=decoded, pickup_payload=pickup_payload)
```

⚠️ **決済前に必ず `decode_hex()` で再検証する。**
表示した `store_id / 金額 / 商品列 / 受取方法` と実際に送る内容が一致することを照合し、
不一致なら即中断する。利用者が貼った hex を無検証で信用しない（金額改ざん対策）。

`_build_store_order_body()` は `field 7` が空固定のため、**pickup_payload を注入できるよう
フォーク実装する**（`docs/01` §11）。V-1 が未確定の間は「テイクアウト」のみ選択可とし、
他の選択肢は無効化して「準備中」と表示する。

### 5.5 アカウント選択スコアリング

```
score = 3.0 × (status == ACTIVE)
      + 2.0 × (store_group_cache の group と相性が良い)

      + 1.0 × (トークンが有効)
      − 5.0 × consecutive_failures
```

## 6. レシート画像生成（R-10）

添付画像3は**可変要素が注文番号のみ**。重い HTML→PNG は不要。

### 6.1 テンプレート実測値（測定済み・そのまま使用してよい）

`assets/templates/receipt.png`（添付画像3）を解析した結果:

| 項目 | 実測値 |
|---|---|
| 画像サイズ | **370 × 665 px**（RGBA） |
| 「7161」の外接矩形 | **x: 191–319 / y: 111–158**（幅 129 / 高さ 48） |
| 数字の中心 | **(255, 134)** |
| 背景色 | **`(247, 247, 247)`** |
| 数字の色（インク） | **`(45, 45, 45)`** |
| 推定フォントサイズ | **約 66 px**（数字高さ48px ÷ キャップ比0.72） |

### 6.2 実装

```python
# services/receipt.py
TEMPLATE   = "assets/templates/receipt.png"
FONT       = "assets/fonts/NotoSansJP-Bold.ttf"

CLEAR_BOX  = (150, 103, 362, 168)   # 元の番号を消す領域（余白込みで広めに取る）
CENTER     = (255, 134)             # 描画の中心
BG_COLOR   = (247, 247, 247)
INK_COLOR  = (45, 45, 45)
BASE_SIZE  = 66                     # 4桁のときの基準サイズ
MAX_WIDTH  = 200                    # これを超えたら縮小する

async def render(receipt_number: str) -> io.BytesIO:
    def _draw():
        img = Image.open(TEMPLATE).convert("RGB")
        d   = ImageDraw.Draw(img)
        d.rectangle(CLEAR_BOX, fill=BG_COLOR)

        # 桁数が変わっても収まるようにフォントサイズを自動調整
        size = BASE_SIZE
        while size > 20:
            font = ImageFont.truetype(FONT, size=size)
            l, t, r, b = d.textbbox((0, 0), receipt_number, font=font)
            if (r - l) <= MAX_WIDTH:
                break
            size -= 2

        d.text(CENTER, receipt_number, font=font, fill=INK_COLOR, anchor="mm")
        buf = io.BytesIO(); img.save(buf, "PNG"); buf.seek(0)
        return buf
    return await asyncio.to_thread(_draw)
```

- テンプレートは**画像3をそのまま使用**（R-10 / E-3: 運営の自己責任判断）
- **`CLEAR_BOX` は数字の外接矩形より広く取る**。狭いとアンチエイリアスの縁が残る
- 実装後、`7161` を描画して**元画像と重ねて差分を確認**すること（V-7 の検証）
- フォントは太さを合わせる必要がある。Noto Sans JP Bold で合わない場合は Black を試す
- 所要時間は約 30〜60ms。DM 送信時に `discord.File(buf, filename="receipt.png")` として添付

## 8. スラッシュコマンド二重表示の解消（R-13）★

### 8.1 原因

Discord でコマンドが2つずつ表示される最も一般的な原因は、
**同一コマンドがグローバルとギルドの両スコープに登録されている**こと。
過去に `tree.sync(guild=...)` を実行したことがあると、その**ギルドコマンドは
グローバル同期に切り替えた後も残り続ける**。

加えて現行 `main.py` は `command_prefix="/"` を設定しており、
プレフィックスコマンドとスラッシュコマンドが併存しうる構造になっている。

### 8.2 対策（必ず実装すること）

```python
class Bot(commands.Bot):
    def __init__(self):
        super().__init__(
            command_prefix=commands.when_mentioned,   # ★"/" をやめる
            intents=discord.Intents.default(),        # message_content は使わないので外す
            owner_ids=OWNER_IDS,
            help_command=None,
        )
        self._synced = False

    async def on_ready(self):
        if self._synced:
            return
        # ① スコープを必ずどちらか一方に寄せる
        if GUILD_ID:
            # ギルド運用: グローバルを空にしてからギルドへ
            self.tree.clear_commands(guild=None)
            await self.tree.sync()
            guild = discord.Object(id=GUILD_ID)
            self.tree.copy_global_to(guild=guild)
            await self.tree.sync(guild=guild)
        else:
            # グローバル運用: 参加中の全ギルドの残留コマンドを一掃
            for g in self.guilds:
                self.tree.clear_commands(guild=g)
                await self.tree.sync(guild=g)
            await self.tree.sync()
        self._synced = True
```

**さらに守ること**

1. **`setup_hook` で sync しない。** `setup_hook` の時点では `self.guilds` が空で残留分を掃除できない。
2. **同期はコマンド定義が変わったときだけ**。定義のハッシュを `.sync_state.json` に保存し、
   一致したらスキップする（同期APIは厳しいレート制限がある）。
3. **`app_commands.command` と `commands.hybrid_command` を混在させない。**
   `hybrid_command` はスラッシュとプレフィックスの両方を登録するため、二重表示の原因になる。
4. **BOT を二重起動しない。** `admin.py` の `os.execv` による再起動は、
   旧プロセスが残ると多重起動になる。PIDファイルによる二重起動防止を入れる。
5. `/sync` はオーナー限定コマンドとして用意し、**手動実行時のみ**同期する。

## 9. 絵文字ポリシー（R-13）

**カスタム絵文字（`<:name:id>` 形式）は使用しない。** サーバーを跨ぐと表示されないため。
Unicode 絵文字のみを `emoji.py` に定数化して使う。

