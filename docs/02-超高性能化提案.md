## 🔴 Tier S — これが無いと金銭事故が起きる

### S-1. 注文 Saga（分散トランザクション状態機械）

`StoreOrder` → `AuthoriseOrder` → `GetPaidOrder` は別リクエストで、**間で必ず落ちうる**。
「残高だけ減って商品が来ない」「課金されたのに注文番号が分からない」を構造的に防ぐ。

```
CREATED → QUOTED → BALANCE_HELD → MCD_STORED → MCD_AUTHORISED
        → RECEIPT_FETCHED → BALANCE_CAPTURED → NOTIFIED → COMPLETED
                                │
                                ├─(失敗)→ COMPENSATING → REFUNDED
                                └─(MCD_AUTHORISED以降の失敗)→ MANUAL_REVIEW ⚠️
```

**鉄則**: `MCD_AUTHORISED` に到達した後は**自動返金してはいけない**。
実際に課金が成立している可能性があるため、必ず管理者レビュー行きにする。

- 各状態遷移を DB に**同期コミット**（メモリ上の状態は信用しない）
- BOT 起動時に `COMPLETED / REFUNDED / MANUAL_REVIEW` 以外の saga を**自動再開**
- `order_token` があれば `GetPaidOrder` で結果を復元できる → 復旧の主経路

### S-2. 冪等性キー（二重注文の防止）

Discord のボタンは**連打できる**。3秒タイムアウトで再送もされる。

- 注文確定ボタンに `idempotency_key = uuid4()` を埋め込み、DB に UNIQUE 制約
- 同一キーの2回目以降は**既存 saga の状態を返すだけ**
- 併せて `user_id` 単位の**進行中注文ロック**（同時に1注文まで）

### S-3. 残高は「引き落とし」ではなく「ホールド → 確定」

```
① 見積確定       hold(user, 自己負担額)      → available 残高が減る
② 決済成功       capture(hold_id)           → 確定
③ 決済失敗       release(hold_id)           → 全額戻る
```

### S-4. 複式簿記 Ledger（append-only）

残高カラムを直接 UPDATE する設計は**必ず壊れる**。

```sql
CREATE TABLE ledger (
  id            BIGSERIAL PRIMARY KEY,
  tx_id         UUID NOT NULL,              -- 同一取引の借方/貸方を束ねる
  account       TEXT NOT NULL,              -- 'user:123' / 'subsidy_pool' / 'kyash:1'
  amount        BIGINT NOT NULL,            -- 正=入金 / 負=出金
  kind          TEXT NOT NULL,              -- charge/hold/capture/release/subsidy/adjust
  order_id      UUID,
  memo          TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 不変条件: SELECT SUM(amount) FROM ledger WHERE tx_id = ? → 必ず 0
```

残高は `SUM(amount)` の集計 or マテビューで導出。**整合性検査コマンドを定期実行**。

### S-5. hex ラウンドトリップ検証

生成／受領した hex は**決済前に必ず** `decode_hex()` で再パースし、
`store_id / amount / product_id列 / pickup_method` が表示内容と一致することを照合する。
不一致なら即中断。**利用者が貼った hex をそのまま信用しない**（金額改ざん対策）。

### S-6. 同期I/Oによるイベントループ停止の回避 ⚠️

**HATTIMCD は `requests` ベースの完全同期ライブラリ**。
discord.py（asyncio）から直接呼ぶと、注文中（数秒〜十数秒）**BOT全体が完全に固まる**。

対策（いずれか）:
- **[簡易]** `await asyncio.to_thread(mcd.pay_from_hex, hex_str)` で必ずラップ
- **[推奨]** HATTIMCD を `httpx.AsyncClient` ベースへ移植した `mcd_async.py` を自前で持つ
  （エンドポイント/ボディ構築ロジックは `docs/01` に全て記載済みなので移植は容易）

## 🟠 Tier A — 体感速度を劇的に上げる

### A-1. TokenVault（トークンキャッシュ）

現状は API 呼び出しのたびに `access_token` + `root_paseto` を再取得（1注文で無駄な往復4回以上）。

- アカウント単位で `access_token` / `root_paseto` / `pos_paseto` を TTL 付きキャッシュ
- **期限60秒前にプロアクティブ更新**、401 受信時のみ強制再取得して1回だけリトライ
- バックグラウンドで全アカウントのトークンを**45分ごとにウォーム**
- `refresh_token` はローテーションするため、**取得のたびに即DB永続化**（`docs/01` §2-A）

→ 注文確定〜完了の往復が **8回以上 → 3回程度**に削減。

### A-2. 投機的先読み（Speculative Prefetch）★効果大

利用者が hex を入力してパネルが開いた瞬間、**確定ボタンを押す前に**バックグラウンドで:

```
decode_hex        （ローカル・即時）
get_store_name    （店名表示に必要）
store_id → group  （キャッシュ解決 or 特定）
pos_paseto 取得   （該当 group 分を先に取る）
root_paseto ウォーム
```

確定押下時に残るのは `StoreOrder` + `AuthoriseOrder` + `GetPaidOrder` の3回のみ。
**「押した瞬間に終わる」体験**になり、これが最も“超高性能”を感じさせる。

### A-3. store_id → group 解決キャッシュ

`store_order()` は group-e〜h を総当たり（最悪8リクエスト無駄）。

```sql
CREATE TABLE store_group_cache (
  store_id    TEXT PRIMARY KEY,
  group_name  TEXT NOT NULL,
  store_name  TEXT,
  resolved_at TIMESTAMPTZ NOT NULL,
  hit_count   INT NOT NULL DEFAULT 0
);
```

2回目以降の同一店舗は**一発で当たる**。未知店舗も、当たった group を即記録。

### A-4. 進捗リアルタイム表示

確定後、**同一メッセージを編集し続けて**進捗を見せる（無言待機をゼロにする）。

```
⏳ 注文処理中…
✅ ① 残高を確保しました        （¥354）
✅ ② 店舗を照合しました        （10528 / 〇〇店）
🔄 ③ マクドナルドへ送信中…
⬜ ④ 注文番号を取得
```

→ 完了時に **DMへ画像1・画像2のパネルを送信**。

## 🟠 Tier A — アカウント運用を壊さない

### A-5. アカウント健全性管理 + サーキットブレーカー

```
ACTIVE ──(連続失敗3回)──▶ DEGRADED ──(失敗継続)──▶ QUARANTINED ──▶ BANNED
   ▲                                                      │
   └──────────(ヘルスチェック成功)────────────────────────┘
```

- `QUARANTINED` になったら**即座にプールから外し、管理者へDM通知**
- 別アカウントへ**自動フェイルオーバーして注文を継続**（利用者からは見えない）
- 定期ヘルスチェック: `get_user_tags()` 等の軽いAPIで生存確認

### A-6. アカウント選択スコアリング

単純ラウンドロビンではなく重み付けで選ぶ:

```
score = 3.0 × (Kyash残高が足りるか)
      + 2.0 × (店舗 group と相性が良いか)
      + 1.5 × min(最終使用からの経過時間 / 30分, 1.0)
      + 1.0 × (1 - 当日注文数 / 日次上限)
      - 5.0 × (直近失敗回数)
```

### A-7. デバイスフィンガープリントの分離 ⚠️

`docs/01` §7 の通り、現状は**全アカウントが同一端末ID・同一座標（京都固定）**。

```sql
ALTER TABLE mcd_accounts ADD COLUMN device_uid        UUID;  -- x-vmob-uid
ALTER TABLE mcd_accounts ADD COLUMN wmop_device_id    UUID;  -- x-wmop-deviceid
ALTER TABLE mcd_accounts ADD COLUMN fb_instance_id    TEXT;  -- x-fb-instance-id
ALTER TABLE mcd_accounts ADD COLUMN home_lat          NUMERIC;
ALTER TABLE mcd_accounts ADD COLUMN home_lng          NUMERIC;
ALTER TABLE mcd_accounts ADD COLUMN proxy_url         TEXT;  -- 任意
```

アカウント作成時に**一度だけ生成して固定**（毎回ランダムだと逆に不自然）。
座標は**注文店舗の近傍に微小ノイズを乗せて**生成すると自然。
`MCD.__init__` は既に `proxy` 引数を持つのでプロキシ割当はそのまま使える。

## 🟡 Tier B — 機能の厚み

### B-1. メニューカタログ & Discord上での注文組み立て

mcdon.asia に依存せず**BOT内で完結**させる本命機能。

1. `data.cat.{group}.prod.mop.mcd.qorcommerce.com/{store_id}.json` を夜間バッチで巡回
2. 商品マスタ（`product_id` / 名称 / 価格 / カテゴリ / アドオン構造 / 提供時間帯）をDB化
3. Discord UI:
   ```
   /order → [店舗検索(オートコンプリート)] → [カテゴリ選択] → [商品選択]
          → [サイズ/セット/アドオン Modal] → [カート編集 ±/削除]
          → [受取方法選択] → hex生成 → decode_hex で検算 → [確定]
   ```
4. 朝マック等の**時間帯制限・店舗別価格差・売切れ**を反映

> ※ `data.cat` JSON に商品マスタが含まれるかは **要検証 V-4**。
>   含まれない場合は mcdon.asia 解析 or 手動CSVインポートにフォールバック。

### B-2. ワンクリック再注文

過去注文（hex + 店舗 + 受取方法）を保存し、DMパネルに「🔁 同じ注文をもう一度」ボタン。
価格変動時は差分を明示して再確認。

### B-3. バズー（呼び出し番号）通知

`get_order_buzzer_notification(order_token)` を注文後ポーリングし、
**「🔔 できあがりました！カウンターでお受け取りください」**を DM 追撃送信。
体験価値が非常に高い割に実装コストは小さい。

### B-4. 予約注文

`/order --at 12:30` で指定時刻に自動実行。混雑回避に有効。
残高ホールドは予約時、決済は実行時。

### B-5. 負担率ポリシーエンジン

単一のグローバル率ではなく、**優先度付きルール**で解決:

```
優先度 1: ユーザー個別上書き
優先度 2: キャンペーン（期間限定・対象店舗/商品）
優先度 3: ロール別（Booster 70% / 一般 50% …）
優先度 4: グローバル既定値

+ 1注文あたり負担上限 / 1日あたり負担上限 / 月間負担上限
+ 端数処理方式（切上/切捨/四捨五入）を明示設定
```

負担額は必ず `subsidy_pool` 勘定から Ledger に記帳（S-4）。

### B-6. 感想ゲート（画像1の機能）

```
注文完了 → user.feedback_required = TRUE, pending_order_id = X
   → DM で返信を受信
       ├ テキストあり → 解禁 + 実績チャンネルへ転載（写真も添付）
       └ 写真のみ     → 「⚠️ 写真だけでは解禁されません」と案内
   → 次回注文時に feedback_required を判定してブロック
```

管理者用の**免除コマンド** `/feedback waive @user` も用意。

### B-7. 実績チャンネル

- 完了時に **embed + レシート画像**を投稿
- **感想が届いたら同じメッセージを編集して追記**（スレッドが汚れない）
- 匿名化オプション（ユーザー名を伏せる / ロールのみ表示）
- 日次サマリ自動投稿: 注文数 / 総額 / 負担総額 / 人気商品TOP5

### B-8. レシート画像生成（画像2・3の再現）

添付画像3は**可変要素が注文番号のみ**なので、重い HTML→PNG は不要。

- **推奨: Pillow + テンプレートPNG**（約30〜60ms・依存が軽い）
  1. 画像3を `assets/templates/receipt.png` として保持
  2. 番号領域を背景色で塗りつぶし
  3. Noto Sans JP Bold で `receipt_number` を中央揃え描画
  4. `discord.File` で DM 添付
- 代替: Playwright で HTML→PNG（再現度は高いが 300ms〜・メモリ数百MB）
- **フォント・ロゴはリポジトリに同梱し、ライセンスを確認**（`docs/01` §9-3）

## 🟢 Tier C — 運用・信頼性

### C-1. 技術スタック（推奨）

| 層 | 選定 | 理由 |
|----|------|------|
| 言語 | Python 3.11+ | HATTIMCD / Kyashモジュールが Python |
| Discord | discord.py 2.4+（既存 cogs 構成を継承） | 既存資産をそのまま活かせる |
| DB | PostgreSQL + SQLAlchemy 2.0(async) + Alembic | Ledger の同時実行制御・トランザクション |
| キャッシュ | Redis（単一プロセス運用なら省略可） | TokenVault / 分散ロック |
| HTTP | httpx(async) — MCD ラッパー移植用 | S-6 のイベントループ対策 |
| 画像 | Pillow | B-8 |
| 配備 | Docker Compose（bot + postgres + redis） | 再現性 |

### C-2. 秘密情報の保護

- `refresh_token` / Kyash 認証情報 / `card_id` は **AES-GCM または Fernet で暗号化カラム**に保存
- 鍵は環境変数（`.env` は `.gitignore`）
- **PAN・CVV は一切保存しない**
- ログに token / hex 全文を出さない（先頭8文字＋マスク）

### C-3. レート制御

- ユーザー単位トークンバケット（例: 10分に1注文）
- グローバル同時注文セマフォ（MCD API への同時接続数を制限）
- アカウント単位の日次注文上限

### C-4. 不正検知

- 複数 Discord アカウントでの重複受給（同一受取店舗 + 近接時刻 + 同一Kyash）
- 短時間の連続注文 / 異常に高額な注文
- 月間負担上限の到達アラート
- 疑わしい注文は `MANUAL_REVIEW` へ送り、管理者チャンネルに承認ボタン付きで投稿

### C-5. 可観測性

- 構造化ログ（JSON）+ Sentry
- `/stats` コマンド: 注文数 / 成功率 / 平均所要時間 / アカウント別使用量 / 残高整合性
- アカウントが `QUARANTINED` になったら管理者へ即DM
- Ledger 整合性チェック（`SUM(amount) per tx_id == 0`）を毎時実行

### C-6. テスト戦略

| 種別 | 対象 |
|------|------|
| プロパティテスト | hex encode → decode ラウンドトリップ（任意の商品構成で不変） |
| 障害注入テスト | Saga の各状態でプロセスを落として再開できるか |
| モックサーバ | MCD API のスタブで注文フロー全体をCI実行 |
| Ledger 不変条件 | 並行注文時に残高がマイナスにならない |

### C-7. 将来拡張

- FastAPI による Web 管理ダッシュボード（負担率・アカウント・実績をブラウザ管理）
- マルチギルド対応（テナント分離）
- 3DS カード登録の半自動化（管理者向けに ACS URL をDMして完了を待つフロー）
