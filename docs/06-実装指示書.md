## 0. 絶対に守るルール

1. **`AuthoriseOrder` をリトライしてはいけない。** 二重課金になる。失敗時は `GetPaidOrder` で状態を確認する。
2. **`MCD_AUTHORISED` 以降の失敗で自動返金してはいけない。** `MANUAL_REVIEW` に送り管理者へ通知する。
3. **`refresh_token` は更新のたびにローテーションする。** 取得したら同一トランザクションで即保存する。保存漏れ＝アカウント永久ロスト。
4. **同期ライブラリ（HATTIMCD / Kyasher）を `await` なしで直接呼んではいけない。** 必ず `asyncio.to_thread()` で隔離する。
5. **残高を UPDATE で直接書き換えてはいけない。** 必ず `ledger` への記帳で表現する。
6. **決済前に必ず hex をラウンドトリップ検証する。** 表示内容と送信内容の一致を確認する。
7. **カード番号(PAN)・CVV を保存してはいけない。** `card_id` のみ。
8. **`setup_hook` でコマンドを同期してはいけない。** `docs/04` §8 の手順に従う。
9. **カスタム絵文字を使ってはいけない。** `emoji.py` の Unicode 定数のみ。
10. **トークン・パスワード・hex・リンクURL を平文でログに出してはいけない。**

## 6. 実装中にテストで検出した不具合の記録

設計段階では気づけず、実際に動かして初めて見つかったもの。
同種の実装をするときの参考に残しておく。

| # | 不具合 | 影響 | 対処 |
|---|---|---|---|
| 1 | SQLite は `BIGINT` 主キーを自動採番しない | 元帳への記帳が全て失敗 | `BigInteger().with_variant(Integer, "sqlite")` |
| 2 | **同時実行で残高がマイナスになる** | ¥1,000 に対し ¥300×10件が全部通り **−¥2,000** | `core/locks.py` で利用者ごとに直列化。ロック外の記帳は例外で停止 |
| 3 | `greenlet` が requirements に無い | 起動すらできない | 追加 |
| 4 | **決済リクエスト中に通信が切れると自動返金していた** | 課金の成否が不明なまま残高を戻す＝二重の損失 | `MCD_AUTHORISING` 状態を追加。`GetPaidOrder` で確認できなければ手動確認へ |
| 5 | アカウント削除時に過去の注文が外部キー違反 | 削除できない | `ON DELETE SET NULL` |
| 6 | タスクループを `cog_load` で開始すると静かに死ぬ | 定期処理が一切動かない | `on_ready` へ移動 |
| 7 | 日次リセットとバックアップが同じフラグを共有 | リセットが毎時走る | フラグを分離 |
| 8 | 復旧のたびに利用回数が二重に増える | 通算回数がずれる | 確定時に1回だけ加算 |
| 9 | 復旧済みの注文が毎起動で拾われ続ける | 無限に復旧処理が走る | 復旧後に `COMPLETED` へ |
| 10 | 商品を足してもカート表示が古いまま | 操作が分かりにくい | 同一メッセージ内で遷移するよう統一 |
| 11 | チャージ額が確定する前に受取口座を選んでいた | 月間上限を超えうる | 金額確定後に選び直す |
| 12 | 注文コードの受取方法が店舗の対応外だと選択肢から消える | 選び直せない | 候補に残す |
| 13 | 商品が未登録なのにETagが残っていると、304で「変更なし」と判断され空のまま | メニューが永久に表示されない | 商品0件ならETagを無視 |
| 14 | 店舗インデックスの再読み込み中に検索できなくなる | 一瞬だけ検索が空振り | 組み立ててから一括差し替え |
| 15 | 店舗クロールで38,000件のタスクを一度に生成 | 1GB環境でメモリ不足 | 2000件ずつ分割 |
| 16 | アカウント未登録のまま注文すると内部エラー | 利用者に原因が伝わらない | 入口で確認して案内 |
| 17 | インデックス読み込み失敗時に古い内容が残る | 検索結果がおかしくなる | 失敗時は空にする |
| 18 | **配信グループを4つ（e/f/g/h）だと判断していた** | `group-i`/`group-j` の **1,379店舗（45%）が注文不可**。山形・福島・福井・山梨・和歌山・鳥取・熊本は県ごと全滅 | `config.MCD_GROUPS` を6つに。店舗数の多い順に並べ替え |
| 19 | **店舗IDを整数として扱っていた** | `01003`（北海道）が `1003` になり、**01〜09の9都道府県を丸ごと取りこぼす** | 文字列のまま扱う。利用者が先頭の0を省いた場合はゼロ埋めして探す |
| 20 | DMを拒否している利用者に控えが届かない | 注文は成立しているのに**店頭で受け取れない** | 控え画像と注文番号を本人にだけ見える形でその場に出す |
| 21 | 店名をひらがなで入力すると0件（`まえばし`） | 一番多い外れ方なのに案内が無かった | 案内文で漢字入力を最初に促す |
| 22 | サイトマップの取得失敗で同期全体が止まる | 店舗の巡回更新まで行われない | 照合の失敗と巡回更新を切り離す |
| 23 | 配信元に無い店舗IDを毎回6グループ総当たり | 15分ごとに無駄な通信 | 24時間あけて再挑戦 |
| 24 | 通信ライブラリが1リクエストごとにINFOログ | 15分ごとに数百行流れてログが読めない | `httpx`/`httpcore` を警告のみに |
| 25 | コマンド重複テストが親グループを見ていなかった | `/config menu interval` と `/config store interval` を誤検出 | 呼び出し名まで含めて照合 |
| 26 | **SQLiteは`DateTime(timezone=True)`でもタイムゾーンを保存しない** | 読み戻すとnaiveになり `now - last_used_at` が `TypeError`。**注文が一切通らなくなった** | `db.models.as_utc()` を通してから計算。DBを往復する実テストを追加 |
| 27 | 保存前のオブジェクトは列の既定値(0)が入っておらず`None` | `orders_today / 20.0` で落ち、アカウントを1つも選べない | 数え上げは `or 0` で補う |
| 28 | **提供時間帯の判定に`datetime.now()`（サーバーのtz依存）** | UTC環境だと9時間ずれ、**朝マックが一切選べない**。いまJSTで動いているのは偶然 | `config.now_jst()` で日本時間を明示 |
| 29 | **提供時間帯の日付キーをUTCで作っていた** | 日本時間の0〜9時は前日のキーを見るため、時間帯が一件も取れない | `config.today_jst()` を使う |
| 30 | 日次リセット・バックアップ・「本日の件数」がUTC基準 | 日本の朝9時に切り替わる | すべて日本時間基準に |
| 31 | 注文履歴の時刻がUTC表示 | 日本の利用者には9時間ずれて見える | 日本時間に変換して表示 |
| 32 | **セットの選択枠の中間ノードが抜けていた** | ドリンク枠は `9997918 → 9997914 → 3120` の3段だが2段で作っていた。**セットが注文できない** | `services/mcd/slot_bridge.py` を追加。実物の対応を持ち、貼られた注文コードからも学ぶ |
| 33 | **既定のままの具材を全部送っていた** | 実物にはセットの中のバーガーも氷も入っていない。余計な中身で弾かれる | 変えた具材だけ送る |
| 34 | **field 1 のフラグを全要素に付けていた** | 実物は「子を持つ中間ノードだけ」に付く。最上位と実商品には付かない | 持っている値を信じず構造から決める |
| 35 | **日本時間の値をSQLの比較に使っていた** | DBはUTCのタイムゾーン無しで保存している。日本時間のまま条件にすると9時間ずれ、「本日の件数」も不正検知も合わない | `config.to_db()` / `jst_midnight_utc()` を通してから比較する |

> **教訓**: 2 と 4 はどちらも「テストを書くまで気づかなかった金銭事故」だった。
> 元帳と状態機械は、必ず**同時実行テストと障害注入テスト**を書くこと。
>
> 35 は26（naiveとawareの引き算）と同じ根から出た別の形。
> **日付の区切りは日本時間で決め、DBと比べる前にUTCへ直す**のが規則。
> 表示は日本時間、比較はUTC、と覚えること。
>
> 32〜34 は**実物の注文コードとバイト単位で突き合わせるまで分からなかった**。
> 構造が1段違うだけ、フラグが1バイト多いだけで相手は受け付けない。
> カタログから組み立てる場合は、**実物と完全に一致するか**を必ず確かめること。
> `tests/test_set_order.py` が実物との一致を検証している。
>
> 26〜29 は**モックでは絶対に見つからない**類の不具合だった。
> 26 はDBを往復して初めて型が変わる。28・29 はサーバーのタイムゾーンが
