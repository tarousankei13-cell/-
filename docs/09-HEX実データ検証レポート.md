## 2. 確定した HEX スキーマ

```
1  storeId               string          "13934"
3  createPaymentMethod   message
   └ 8 { 1: successUrl, 3: failUrl }     ※mcdon.asia経由の場合はそのURLが入る
7  createDeliveryMethod  message (oneof) ← docs/07 §4.2
   └ 1 eatIn {} / 2 takeOut {} / 3 tableDelivery / 4 curbsidePickUp
     5 driveThru / 6 addressDelivery
8  order                 message
   └ 2  item  (repeated)  ★複数商品なら field 2 が複数並ぶ
        ├ 2  productCode   string   "9180"
        ├ 3  quantity      varint   1
        ├ 4  totalAmount   varint   800
        └ 5  component     (repeated / 再帰)
             ├ 1  (present flag)  varint 1
             ├ 2  productCode     string   "9987009"（選択枠）
```

## 3. 🐛 HATTIMCD のバグ（追加2件・計4件）

### 3.1 `8.2.2` は `shortOrderCode` ではなく `productCode`

```python
# HATTIMCD decode_hex()
for v in f2.get(2, []):
    short_code = _try_str(v)      # ❌ 実際には productCode ("9180")
```

`_build_store_order_body` で同じ位置に書き戻すため**往復では壊れない**が、
`DecodedOrder.short_order_code` の値は商品コードであり、意味が誤っている。
BOT 側では `product_code` として扱うこと。

> あわせて `amount_cents` も名前が誤り。**単位は「円」**であって cents ではない。

### 3.2 ⚠️ 複数商品の注文が壊れる

```python
for f2_raw in _proto_parse(f8_raw).get(2, []):   # 商品ごとにループするが
    f2 = _proto_parse(f2_raw)
    for v in f2.get(2, []): short_code = _try_str(v)   # ❌ 上書きされる
    for v in f2.get(4, []): amount = v                 # ❌ 上書きされる
    for pr in f2.get(5, []): products.append(...)      # 構成品だけが合算される
```

商品が2点以上ある HEX では:
- `short_code` と `amount` が**最後の商品の値で上書き**される
- `_build_store_order_body` は**1商品にまとめて**送ってしまう

→ **BOT 側では `DecodedOrder.items: list[OrderItem]` として複数商品を保持する構造に作り直すこと。**

```python
@dataclass
class OrderItem:
    product_code: str
    quantity: int
    amount: int
    components: list["OrderItem"]

@dataclass
class DecodedOrder:
    store_id: str
    pickup_method: str
    items: list[OrderItem]          # ★複数商品に対応
    total_amount: int               # sum(item.amount)
```

> **要検証**: `8.2.4` が「その商品の金額」か「カート合計」か。
> 単一商品の検証では区別できなかった。2点以上の HEX で確認すること（V-9）。

## 4. 実運用で判明したこと — HEXは壊れやすい

今回いただいた HEX は、**2バイト（商品コードの1文字ずつ）が欠落**していた。
コピー時の取りこぼしと思われる。

```
受け取った値: ...1207 393937393138 ...   → "997918"（6バイト）
長さプレフィックス 0x07 は 7バイトを要求 → 不整合
正しい値:     ...1207 39393937393138 ... → "9997918"（7バイト）✅ カタログに存在
```

### 設計への反映（`docs/04` §5.4 を強化）

HEX を受け取ったら、決済前に**3段階の検証**を必ず行う。

| 段階 | 検証内容 | 失敗時 |
|---|---|---|
| ① 構文 | protobuf として完全にパースできるか（**長さプレフィックスと実バイト数の一致**） | 「注文コードが壊れています。もう一度コピーしてください」 |
| ② 意味 | `storeId` が実在し、全 `productCode` がその店舗のカタログに存在するか | 「この店舗では取り扱いのない商品が含まれています」 |
| ③ 金額 | カタログから再計算した合計が `totalAmount` と一致するか | ⚠️ **即中断**。改ざんの可能性があるため管理者へ通知 |

> ③ は**金額改ざん対策の要**。今回「メニューJSONから計算した金額がHEXと一致する」ことを
> 実証できたので、この検証は**確実に実装できる**。

さらに、①で長さ不整合を検出したら、**長さプレフィックスを手がかりに自動修復を試みる**とよい。
今回の欠落は自動復元できた（復元後、カタログ照合も通った）。

# 中間ノードの「不要」を記録していなかった（2026-10-06 修正）

## 何が起きたか

V-12 で「`9987016` / `9987017`（ハッピーセット）は**中間ノード不要**」と
確認済みだったのに、**その事実がコードのどこにも入っていなかった。**

`slot_bridge.KNOWN` は「枠 → 中間」しか持たない。中間が不要な枠は
そこに載らないので、`bridge_for()` は空文字を返す。

⚠️ **空文字は「不要」と「不明」の両方を意味していた。** 区別が付かない。

結果、利用者に「ハッピーセットの中間ノードが分からないので、実物の
注文コードを下さい」と求めてしまった。**不要と確認済みのものだった。**

## 直し方

`NO_BRIDGE` を追加し、「実物で中間なしを確認した枠」を記録する。

```python
NO_BRIDGE = {
    "7251":    "6048",   # ナゲットのソース枠 → バーベキューソース
    "9987009": "2020",   # セットのサイド枠 → ポテトM
    "9987010": "5010",   # セットのサイド枠 → ハッシュポテト
    "9987017": "3315",   # ハッピーセットのドリンク枠 → オレンジ(S)
}
```

`status_of()` が3つに分ける。

| 返り値 | 意味 |
|---|---|
| `bridge` | 中間あり（値を知っている） |
| `direct` | 中間不要と**実物で確認済み** |
| `unknown` | 分からない。調べる余地がある |

⚠️ 送るコードは `direct` と `unknown` で同じ（枠の直下に商品）。
   それでも区別する理由は、**調べる必要があるかどうかが違う**から。
   混ぜると、直す必要の無いものを追いかけることになる。

## ⚠️ `9987016` を NO_BRIDGE に入れなかった理由

V-12 は「`9987016` / `9987017` は不要」と書いているが、**実物で
見たのは `9987017 → 3315` だけ**。`9987016` は「同じハッピーセットの
ドリンク枠だから」という推測で、観測していない。

これは V-10 で失敗したのと同じ推測の形である。
（「同じカテゴリの枠は同じ中間ノードを使う」とみなして
`9997925` に `9997914` を当てたが、実物は `9997922` だった）

**観測していないものは `unknown` のままにする。**
NO_BRIDGE に入れるのは、枠の直下に商品が来ている実物を見たものだけ。

## 現状（店舗 13934）

| | 件数 |
|---|---|
| 中間あり（確認済み） | 2 枠 |
| 中間不要（確認済み） | 4 枠 |
| **まだ分からない** | **24 枠 / 47 商品** |

`/debug bridges` で、いつでもこの一覧が見られる。

# V-13 複数の商品が1品に潰れていた（2026-10-07 確定）

## 症状

```
カート   三角チョコパイ いちご ¥200
         三角チョコパイ 黒     ¥190
         シャカチキ            ¥250
         ───────────────────────
         ご案内した金額 ¥640

マクドナルドの返事   実際の金額 ¥250   ← シャカチキ単体
```

**¥250 はカートの最後の1品ちょうど。**

## 原因：`field 8` の作り方

公式の定義（マクドナルドのアプリから取得・docs/04）：

```
CreateOrderInput { 8: repeated OrderItem items }   ← 繰り返し
OrderItem        { 2: OrderProduct   product }     ← ★単数★
```

このbotは `field 8` を**1つだけ**作り、その中に `field 2` を商品の数だけ
並べていた。

```python
order = b"".join(pb_msg(2, build_item(i, top_level=True)) for i in items)
body += pb_msg(8, order)          # ← field 8 が1つ
```

`product` は**単数**なので、protobuf の規則で複数の値は**併合**される。
数値と文字列は**後の値が前を上書きする**。

```
送った中身            相手が読んだ結果
  2157 ¥200  ┐
  2139 ¥190  ├→  productCode=2080  unitPrice=250   （最後だけ残る）
  2080 ¥250  ┘
```

## 直し方

商品1つにつき `field 8` を1つ作る。

```python
body += b"".join(
    pb_msg(8, pb_msg(2, build_item(i, top_level=True)))
    for i in merge_items(items)
)
```

## ⚠️ なぜ長く気づけなかったか

**`decode_hex` が寛容すぎた。**

```python
# ★ 8 → 2 が繰り返しの商品リスト（HATTIMCDは最後の1件で上書きしていた）
for f8 in top.get(8, []):
    for f2 in proto_parse(f8).get(2, []):
        items.append(...)
```

8 も 2 もどちらも繰り返しとして読むので、**自分で作ったコードを自分で
読み返すと3品に見える**。テストも全部それで通っていた。

しかも元のコメントは「HATTIMCD は最後の1件で上書きしていた」と、
他の実装の読み方を**間違いだと決めつけて**いた。実際には
**マクドナルド自身がその読み方をする**（`d.product = …` は代入）。
寛容なデコーダが、エンコーダの誤りを隠していた。

⚠️ **自分の読み方で確かめても意味がない。相手の読み方で確かめること。**
   そのために `decode_as_mcdonalds()` を用意した。検証専用。

## 影響

- **複数の商品を注文すると、最後の1品しか届いていなかった**
- 1品だけの注文は正常（上書きする相手がいないため）
- 同じ商品を複数は正常（`merge_items` が数量にまとめるため）
- ⚠️ **金額の突き合わせが止めていたので、お金は1円も動いていない**
  （`core/saga.py` の `PriceChanged`。決済前に確かめる作りが効いた）

## ⚠️ 新商品とは関係なかった

三角チョコパイが消えたのは「新商品だから」ではなく、
**カートの最後ではなかったから**。古い商品でも同じことが起きる。

実データ（店舗 10528・2026-10-07 取得）で確認したところ、新商品の
表示・時間帯・名前の取得はすべて正しかった。

| 時刻 | 画面に出る商品 | うち注文できないもの |
|---|---|---|
| 08:00 | 128 件 | **0 件** |
| 12:30 | 128 件 | **0 件** |
| 17:30 | 193 件 | **0 件** |
| 22:00 | 193 件 | **0 件** |

# V-14 送信本体でも商品が1品に潰れていた（2026-10-07）

V-13 で `build_hex` を直したが、**同じ誤りが `build_store_order_body` にも
あった。そちらが本番の送信経路**である。

```

```

`build_hex` が作る注文コードは途中の表現にすぎず、実際にマクドナルドへ
送るのは `build_store_order_body`。**片方だけ直しても実際の注文は直らない。**

⚠️ 同じ形の誤りは1か所とは限らない。1つ見つけたら、**同じことをして

# V-15 決済の成否を推測していた（2026-10-07）

公式の定義（docs/04）：

```
GetPaidOrderOutput { 1: isSettled  bool
                     2: Order
                     3: PaymentError }
```

`_probe_paid()` は「注文オブジェクトが返ってくれば成立」と判断していた。

⚠️ **カードを断られた注文にも order_code は付く。**
   不成立を成立と読むと、**お金が動いていないのに利用者の残高を
   引き落とし、「成功しました」と伝える**ことになる。

`isSettled` と `PaymentError` を読み、

| isSettled | 判断 |
|---|---|
| `True` | 成立 |
| `False` / 決済エラーあり | **成立としない**（手動確認へ） |
| 欄が無い（`None`） | 言ってこない応答なので、注文の有無で判断 |

⚠️ `None`（言っていない）と `False`（違うと言っている）を混同しない。
   StoreOrder / AuthoriseOrder の応答にはこの欄が無いので `None` になる。

# V-16 決済の受取方法が takeOut 固定だった（2026-10-07）

```
AuthoriseOrderInput { 1: orderToken / 2: deliveryMethod / … }
```

`build_authorise_body()` は `deliveryMethod` を **takeOut 決め打ち**で
送っていた。店内（eatIn）や席まで（tableDelivery）を選んでも、
決済の段階だけ「お持ち帰り」として送っていたことになる。

# V-17 項目名を「理由」と取り違えていた（2026-10-10）

`services/mcd/errors.py` は応答の本文に含まれる文字列で原因を当てる。
そこに **`payment` と `token` を部分一致で**入れていた。

注文の送信内容には、次の**項目名**がある。

```
createPaymentMethod   messagingToken   userPosIdToken
offersToken           crewToken
```

相手は入力不備のエラーで、この項目名を本文に載せてくる。
すると「組み立てを間違えた」だけのエラーが

- `createPaymentMethod` → `payment` に一致 → **PAYMENT（決済拒否）**
- `messagingToken` → `token` に一致 → **AUTH（ログイン切れ）**

と読まれる。どちらも `_ACCOUNT_FAULT` なので、

> **そのアカウントが即座に隔離される。**

アカウントが1〜2件の運用では、それだけで注文が止まる。
管理者はカードやログインを疑い、本当の原因（送る内容）に辿り着けない。

## 直し方

この2語だけ「**単語として**一致」に変えた。

```python
_WORD_RULES = {PAYMENT: ("payment",), AUTH: ("token",)}

def _word_in(word, haystack):
    return re.search(rf"(?<![a-z0-9_]){word}(?![a-z0-9_])", haystack) is not None
```

`createpaymentmethod` には当たらず、`payment failed` には当たる。

⚠️ これは V-14（`"authoriz"` ⊂ `"unauthorized"`）と**同じ種類**の誤り。
   短い英単語を部分一致で判定語にするときは、
   **送信内容の項目名と被らないか**を必ず確かめる。

# V-18 PayPayのチャージに「起動時の復旧」が無かった（2026-10-10）

⚠️ 自動で記帳してはいけない。残高が増えていない場合に増やすと
   取り返せない。必ず管理者の確認へ回す。
⚠️ 保留（`HELD`）はここで触らない。見張りのループが面倒を見るので、
   要確認にすると自動受け取りが止まる。

# V-19 保留が解けたあと、自分で貼り直せなかった（2026-10-10）

保留になったリンクは、見張りのためにその時点で1行覚える。
`link_uuid` は一意なので、保留が解けたあとに利用者が自分で貼り直すと

> **お金はまだ受け取っていないのに「すでに使用されています」**

と断られていた。利用者からは「送ったのに使えないと言われた」になる。

まだお金が動いていない状態（`HELD` / `FAILED`）なら、その行を
使い直すようにした。受け取り済み（`RECEIVED` / `CREDITED`）と
要確認（`MANUAL_REVIEW`）は、今までどおり断る。

| 失敗した場所 | どうするか | 理由 |
|---|---|---|
| 受け取りを**投げる前** | 保留（見張り）に戻す | お金は動いていない |
| 受け取りを**投げたあと** | 要確認へ | 動いたか分からない。再受け取りは二重取りになる |

# V-20 使用中の印が外れないことがあった（2026-10-10）

同時注文の取り合いを防ぐため、アカウントを選んだ直後に
「使用中」の印を付ける。印を外すのは `AccountHandle.aclose()`。

ところが **印を付けたあとで handle を作る途中に失敗すると**、
呼び出し側は handle を受け取れないので閉じようがない。
印は15分の自動解除まで残り、その間そのアカウントは選ばれない。

アカウントが1〜2件の運用では、**それだけで注文が止まる**。
（直そうとしたバグより悪い。）

選ぶ処理全体を囲み、外へ返せなかった handle は必ず後片付けする。
保存の失敗は `async with` を**抜けるとき**に起きるため、
`try` はその外側に置かないと捕まえられない。

# V-21 セットの見積りが「選んだ中身」を見ていなかった（2026-10-10）

利用者の報告は「**セット系が頼めない**」。

## 何が起きていたか

セットの値段（`prePrice`）は「**参照商品を選んだときの値段**」。
実データ（13934 / 9241 ビッグマック® セット）で検算できる。

```
セット prePrice 810
  = 350  バーガー分（priceList TAKEOUT）
  + 370  サイド枠 9987009 の prePrice  ← ポテトM の単品価格そのもの
  +  90  ドリンク枠 9997918 の prePrice
```

つまり ¥810 は「ポテトM＋コーラM」の値段で、別のものを選べば差額が乗る。
ところが `price_of()` は商品コードだけで定価を引いており、
**その品の components（実際に選んだ中身）を一切見ていなかった。**

```python
p = menu.products.get(str(item.product_code))
return p.price_for(pickup) if p else int(item.amount or 0)   # ← 中身を見ていない
```

この値が `reprice()` を通って注文の `list_price` になる。そして

```python
if stored.total_amount and stored.total_amount != list_price:
    raise PriceChanged(list_price, stored.total_amount)
```

で**必ず**食い違い、決済の直前で中止されていた。

## 影響

実データの店舗（13934・247商品）で、差額が出る組み合わせは **417通り**。
いちばん大きいのはサイドをチキンマックナゲット15ピース（単品¥780 /
参照のポテトMは¥370）にした場合で、**¥410 のずれ**。

```
月見バーガー セット + ナゲット15ピース   見積り¥800 / 実際¥1,210
```

利用者に出るのは

> お値段が変わっていたため、注文を中止しました。

だけなので、原因が分からない。**既定のポテトM＋コーラMだけが通り、
それ以外は全部ダメ**という形になり、「セットが頼めない」と見える。

## 直し方

`choice_upcharge()` を足し、`price_of()` で加算する。

```python
差額 = Σ max(0, 選んだ商品の単品価格 − 参照商品の単品価格)
```

⚠️ これはカタログの計算と**つじつまが合う唯一の式**。
   参照を選べば差額0で、合計はセット価格ちょうど（¥810）になる。
   枠の `prePrice` そのものを引く式では、コーラMを選んだだけで
   ¥220 ずれて実データに合わない。

⚠️ **安いものを選んでも引かない。** `refundThreshold` は 0 で、
   返金の仕組みが無い。引くと運営の持ち出しになる。

⚠️ **実機で確かめたのは参照の組み合わせだけ**（V-1 の実HEXは
   ポテトM＋コーラMで、金額 800 がちょうど一致している）。
   別のものを選んだ注文の記録がまだ無い。もし実際の上乗せ額が
   違っても、金額の照合は決済より前なのでお金は動かない
   （今までどおり中止されるだけ）。確かめたらここに追記する。

## 画面の表示も逆だった

```python
+ (f"（+{embeds.yen(c.extra_price)}）" if c.extra_price else "")
```

`extra_price` は枠の `prePrice`、つまり**セット価格に含まれている額**。
これを「+○円」として出していたので、コカ・コーラMを選んだだけで
「**+90円**」と表示されていた。意味が逆である。
出すべきは差額なので、そう直した。選択肢の一覧にも
「+¥410」のように**選ぶ前**に出す。

## 選択肢には値段を持たないものが混ざる

直した直後、ナゲット5ピースの画面が落ちた。

```
AttributeError: 'Extra' object has no attribute 'price_for'
```

選択枠の候補には `Extra`（ナゲットのソース・ハッピーセットのおもちゃ・
ドレッシング）が混ざる。これは `products` に載らないので価格を持たない。
`price_for` を呼ぶと**画面を作る処理ごと落ち**、利用者には
「BOTは時間内に応答しませんでした」としか見えない。
もともと無料の選択肢なので 0 として扱う（`_unit_price`）。

# V-22 選択枠に「選べないもの」を並べていた（2026-10-10）

利用者が実機（公式アプリ）の画面を見せてくれた。
**チーズチーズ倍月見 セット**のサイド枠に出るのは、たった4つ。

```
マックフライポテト®  サイドサラダ
チキンマックナゲット® 5ピース  えだまめコーン
```

こちらは **14件** 出していた。しかもその中に

```
ポテナゲ大 ¥600 / ポテナゲ特大 ¥980
食べくらべポテナゲ大 ¥630 / 食べくらべポテナゲ特大 ¥990
月見パイ モーニングセット ¥420
```

が入っていた。**どれも VALUE_MEAL、つまりセットそのもの。**
セットの中身にセットを並べていたことになる。選ばせれば、
金額がどうこう以前に注文は必ず断られる。

## 原因

候補は「参照商品が属するカテゴリ全部」から出している
（カタログに枠の中身が書かれていないため）。サイド枠の参照は
マックフライポテトMなので、母集団は「サイドメニュー」17件になる。

価格帯（参照の 0.3〜3.0倍）で絞ってはいたが、参照が¥370なので
上限は¥1,110。¥990のセットも素通りしていた。

## 直したこと

カタログを**全項目**当たったが、「どれが選べるか」のリストは
どこにも無い（`collections` / `groupMenu` / `limitedAbility` /
`customizedCollections` / `employeeMealCollection` /
`valueLunchCollection(s)` / `couponCollection` / `sizeVariants` /
`relatedSets` / `grills` を確認）。完全には絞れないので、
**確実に違うものだけ外す**。

1. **VALUE_MEAL を外す** — セットはセットの中身にできない
2. **時間帯区分が噛み合わないものを外す** — ハッシュポテト
   （BREAKFAST_MENU・¥190）が昼のセット（DAY_MENU）に出ていた

14件 → **8件**。実機の4つは全部残る。

⚠️ 絞りすぎて候補を空にしないこと。空になると、その商品が
   一切注文できなくなる（直す前より悪い）。
   `BREAKFAST_DAY_MENU` と空欄は**どちらとも噛み合う**扱いにした
   （ナゲット5ピースは区分が空だが、昼のセットで選べる）。

## 残っている4件

```
シャカチキ ¥260 / チキンマックナゲット15ピース ¥780
プリプリエビプリオ 5ピース ¥310 / 月見パイ ¥210
```

実機では出ないが、**カタログ上は正しい側の4つと見分けがつかない**。

- `productClass` も `dayPart` も同じ
- `limitedAbility` の時間帯も同じ
- 価格でも分けられない（エビプリオ¥310 とナゲット5ピース¥310 が同額）

エビプリオと月見パイは、実機では「ご一緒にいかがですか？」の
**追加商品**として別枠に出ている。つまり「セットの中身」と
「追加で買うもの」はカタログ上で区別されていない。

残りは実機の画面を見て登録するか、断られた記録から学ぶ
（`slot_rules.allowed`）しかない。

## V-21 の数字を訂正する

V-21 で「差額が出る組み合わせが417通り」と書いたが、**過大**である。
その大半は、そもそも実機で選べない組み合わせだった。

さらに、実機の4つは ¥370 / ¥370 / ¥310 / ¥320 で、
**参照のポテトM（¥370）を超えるものが1つも無い**。
セット価格が¥1,000固定で表示されるのと整合する。
サイド枠には上乗せ自体が存在しない可能性が高い。

⚠️ V-21 の差額計算は残してよい。選べるものが参照を超えなければ
   差額は常に0で、何も変えないため。ドリンク枠に上乗せがあるか
   どうかは、実機のドリンク選択画面を見れば分かる（未確認）。

**8件中5件外れ。**

> 参照より高い野菜生活100 には何も付かない。**

単品価格の差では説明がつかない。サイズ違い（`sizeVariants`）の

カタログは全項目を当たったが、上乗せ額はどこにも無い。

```
products / collections / customizedCollections / groupMenu /

employeeMealCollection / valueLunchCollection(s) / couponCollection
```

## 直し方：当てにいくのをやめる

**計算で出せないものを計算しようとしない。**
マクドナルドは注文を登録した時点（`StoreOrder`）で本当の金額を
返してくる。しかもそこは**決済の前**で、止めれば1円も動かない。

```
① 画面には定価だけ（＋「内容によって変わることがあります」）
② StoreOrder  ←★ 本当の金額が分かる。まだ課金されていない
③ 違っていたら、その金額を見せて本人に確かめる
④ 承知なら、その金額で確保し直してから決済
```

こうすると**上乗せ額を知る必要が無くなる**。新商品が出ても、
組み合わせが増えても、こちら側に手を入れることが無い。

### 守ること

- 補助率はそのまま、**利用者と管理者の負担を両方とも計算し直す**
  （片方だけ直すと帳尻が合わない）
- **残高が足りなければ通さない。** 本人が承知でも払えないものは通せない
- **安くなったぶんは戻す。** 確保したままにすると使えない残高が残る
- **既定は「進めない」。** 時間切れも押し間違いも、お金が動かない側へ
- **確かめる手段が無いときは中止**（復旧処理など、本人に聞けない場面で
  勝手に高い金額を通さない）

⚠️ 画面に当て推量の金額を出さないこと。
   以前は枠の `prePrice`（セット価格に**含まれている**額）を
   「+90円」と表示していた。意味が逆なうえ、正しい上乗せ額でもない。
   **間違った金額を自信ありげに出すのは、出さないより悪い。**

|---|---:|
| `choices` | **0** |
| `prePrice` | **0** |
| `referenceProduct` / `defaultProduct` | **0** |
| `limitedAbility` / `groupMenu` | **0** |

⚠️ **この書き方は言い過ぎだった**（V-26 で訂正）。正しくは

```js
case 7: { u.totalAmount = n.int32(); break }
```

> **あのサイトが「確実」なのは、賢いからではない。
> 値段をマクドナルドに聞いているから。**

- 上乗せ額がいくらか → **持っていない**
- 合計金額 → **StoreOrder の応答から読むだけ**

## 結論

ミラーを作っても、V-22（選べる商品が分からない）と
V-23（上乗せ額が分からない）は**1つも解決しない**。
同じ穴がそのまま移るだけである。

そして「値段をマクドナルドに聞く」という部分は、
**V-23 でこちらに入れた仕組みとまったく同じ**。
すでに同じ土俵に立っている。

## ValidateOrder は値段を教えてくれない

名前から期待したが、**出力に欄が1つも無い**。

```js
ValidateOrderInput  { 1: storeId / 2: totalAmount / 3: repeated products }
ValidateOrderOutput { （decode は全部 skipType。欄なし）}
```

`totalAmount` は**入力**にある。つまり「この中身でこの金額で合って

結局、金額を知る方法は **StoreOrder の応答の `totalAmount`** だけ。
V-23 でそうしたのは正しかった。

## CancelOrder は使える

```

CancelOrderOutput { （欄なし）}
```

金額を見せて断られたとき、**登録しただけの注文がマクドナルド側に
残り続けていた**。決済前なので取り消してよい。後片付けとして呼ぶ。

⚠️ 失敗しても注文の流れを壊さないこと。あくまで片付けで、
   できなくても利用者には影響が無い。

⚠️ **決済の前にだけ使う。** 支払い済みの注文をここで取り消そうと
   しないこと（返金は別の話）。

## 実装で踏んだ穴

取り消しを入れた最初の版で `group` を使ったが、その変数は
**まだ代入されていなかった**（④の決済のところで入る）。
正しくは `info.group`。

⚠️ ここは**失敗したときだけ通る道**。間違えると、いちばん必要な
   場面で `UnboundLocalError` になる。`/debug fails` の `nm()` で
   踏んだのとまったく同じ型の誤り。テストが捕まえた。


# V-26 なぜあのサイトは「何を送るか」まで正確なのか（2026-10-10）

答え：**自分で組んでいないから。**

`index.html` に埋め込まれているスクリプトを読むと、改造は
**1か所しかない**。`window.fetch` を差し替えて、支払いの送信を
横取りしているだけ。

```js
window.fetch = function (...args) {
  let urlStr = args[0] instanceof Request ? args[0].url : String(args[0]);
  // ★ CheckoutOrder を検出したらURLをプロキシ（同オリジン）に書き換え
  if (urlStr.includes('mcdord.OrderService/CheckoutOrder')) {
    ...
    p.then(r => r.clone().json().then(d => {
      if (d && d.status === 'intercepted_success') showModal(d.hexStream);
    }));
    return p;
  }
  return _origFetch.apply(this, args);
};
```

ページ自体はマクドナルドの公式フロントエンドそのもの。

```html
<title>マクドナルド モバイルオーダー | McDonald's Japan</title>
<link rel="icon" href="https://www.mcdonalds.co.jp/favicon.ico" />
<meta name="description" content="日本マクドナルドモバイルオーダーは…" />
```

つまり **商品を選んでいるのも、枠に何が入るか決めているのも、
金額を出しているのも、全部マクドナルド自身のコード**。
サイトの作者は「どれが選べるか」も「上乗せ額」も解いていない。
**解く必要が無かった。**

## こちらとの違い

|  | あのサイト | このBOT |
|---|---|---|
| 正体 | マクドナルドのアプリ＋盗聴1行 | 公開カタログからの**作り直し** |
| 選べる商品 | マクドナルドのコードが決める | カタログに書かれていない（V-22） |
| 上乗せ額 | マクドナルドのコードが出す | カタログに書かれていない（V-23） |
| 注文の構造 | マクドナルドのコードが組む | 中間ノードが24枠不明 |

**同じ土俵ではない。** 向こうは答えを持っている側のコードを
そのまま動かしており、こちらは外から組み立て直している。
賢さの差ではなく、立っている場所の差である。

## だから `/debug learn` が効く

あのサイトが出すHEXは、**マクドナルド自身が組んだ正解の構造**。
それを貼ってもらえば、中間ノードがそのまま手に入る。
ミラーを作る必要は無い。**出てきたHEXを貼るだけでよい。**

⚠️ ただし「どれが選べるか」と「上乗せ額」はHEXからは学べない。
   HEXには**選んだ1通りの結果**しか入っていないため。
   前者は断られた記録から（V-22）、後者は StoreOrder の応答から
   （V-23）取るしかない。
