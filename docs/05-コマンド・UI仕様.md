# 05. コマンド・UI 仕様書

> 絵文字は `emoji.py` の定数のみを使う（`docs/04` §9）。カスタム絵文字は使用しない。
> 全コマンドは `app_commands`（スラッシュ）で実装する。`hybrid_command` は使わない（`docs/04` §8）。

---

## 0. 操作方式の原則 ★最重要

| 対象 | 操作方式 |
|---|---|
| **管理者** | **スラッシュコマンド** ＋ **管理者パネル** |
| **利用者** | ⚠️ **パネルとボタンのみ**（サーバー設定でスラッシュコマンドが使えないため） |

### 0.1 利用者向けスラッシュコマンドは一切作らない

**利用者が使う機能は、すべて常設パネルのボタンから始まる。**
`/order` `/balance` `/charge` のような利用者向けコマンドは**実装しない**。

### 0.2 二層ビュー構成

```
【常設パネル】 timeout=None / custom_id 固定 / bot.add_view() で復元
     チャンネルに貼りっぱなし。再起動しても動く。誰が押してもよい。
          │  ボタン押下
          ▼
【一時ビュー】 timeout=120秒 / ephemeral / 押した本人にだけ見える
     カート編集・受取方法選択・確定。状態はDBに保存する。
```

- **常設パネルの View には状態を持たせない。** 再起動で消えるため
- カート等の状態は **DB に `discord_id` をキーに保存**し、一時ビューはそれを読む
- 一時ビューは**押した本人以外の操作を弾く**（`interaction.user.id` を照合）

### 0.3 常設パネルの実装規約

#### 貼ってあるパネルは自動で最新にする

再起動すると `add_view()` でボタンは**反応するように戻る**。
しかしチャンネルに貼ってあるメッセージの中身（embed とボタンの並び）は
Discord 側に保存されたままなので、**古い内容が残り続ける**。

新しいボタンを足しても、貼り直すか `/panel refresh` を叩くまで
利用者には出てこない。管理者がそれを毎回覚えておくのは無理なので、
`main.on_ready` → `_refresh_panels()` が起動のたびに自動で合わせる。

- 更新処理は `cogs/panel.refresh_all(bot)` の1か所だけ
  （コマンドと起動時で別々に書くと、片方を直し忘れて食い違う）
- ⚠️ ここで何が起きても**起動を止めない**。
  チャンネルが消えていても、例外が出ても、ログに残して先へ進む


```python
class ChargePanel(discord.ui.View):
    def __init__(self):
        super().__init__(timeout=None)          # ★必須

    @discord.ui.button(label="チャージする", emoji="🔗",
                       style=discord.ButtonStyle.primary,
                       custom_id="panel:charge:start")   # ★固定IDが必須
    async def charge(self, itx, button): ...

# main.py の setup_hook で必ず登録する（これが無いと再起動後ボタンが死ぬ）
self.add_view(ChargePanel())
```

> ⚠️ `custom_id` は**永久に変えない**。変えると既に貼ってあるパネルのボタンが反応しなくなる。
> 命名規則: `panel:<パネル名>:<動作>`

## 1.4 注文方式の切り替え

`/config order_mode` で、利用者が使える注文方法を制限できる。

| 値 | 注文の入口 | 「注文コードを作る」ボタン |
|---|---|---|
| `both`（既定） | 方法を選ぶ画面を出す | 表示する |
| `hex` | **直接 HEX 入力モーダル**を開く | 表示する |
| `menu` | **直接 店舗選択**へ進む | **非表示** |

### 実装上の注意

常設パネルは `add_view()` で**全ボタンを登録**し、表示だけを出し分ける。
ボタンを登録から外すと、設定変更前に貼ったパネルのボタンが反応しなくなるため。

```python
OrderPanel(mode=None)    # 復元用: 全ボタンを登録
OrderPanel(mode="menu")  # 設置用: HEXボタンを外して表示
```

非表示のボタンが押された場合（古いパネルなど）は、その旨を案内して終わる。

`/panel admin #チャンネル` で設置。**オーナー／管理者ロールのみ**操作可能。

```
┌─────────────────────────────────────────────┐
│ ⚙️ 管理パネル                                 │
│                                             │
│ 🟢 稼働中 ／ マクドナルド 3件 ／ Kyash 2件      │
│ 本日の注文 12件 ／ 負担総額 ¥4,280            │

  [ 📊 統計 ] [ 💴 負担率 ] [ 🔑 アカウント ]
  [ ⚠️ 要確認 ] [ 🔄 メニュー同期 ] [ ♻️ 更新 ]
```

| ボタン | custom_id | 動作 |
|---|---|---|
| 📊 統計 | `panel:admin:stats` | 注文数・成功率・GMV・負担総額・元帳整合性 |
| 💴 負担率 | `panel:admin:subsidy` | 負担率ルールの一覧・追加・削除 |

## 2. チャージフロー

### 2.1 チャージパネル（常設・指定チャンネル）

```
┌─────────────────────────────────────────────┐
│ 💴 残高チャージ                               │
│                                             │
│ Kyash の送金リンクで残高をチャージできます。    │
│                                             │
│ ▸ Kyash アプリで「送金リンク」を作成          │
│ ▸ 下のボタンからリンクを貼り付け              │
│ ▸ 受け取りが完了すると即座に残高へ反映されます  │
│                                             │
│ ℹ️ 1回のチャージは ¥100 〜 ¥50,000 です       │
│ ⚠️ 請求リンクは受け付けできません              │
│ ⚠️ チャージした残高の払い戻しはできません      │
└─────────────────────────────────────────────┘
   [ 🔗 チャージする ]   [ 👛 残高を確認 ]
```

- `View` は `timeout=None` の永続ビュー。`custom_id` を固定し、`setup_hook` で `add_view()` する
- 再起動後もボタンが生き続けるようにすること

### 2.2 チャージ Modal

```
タイトル: 💴 残高チャージ
 ┌ Kyash 送金リンク ───────────────────────┐
 │ https://kyash.me/payments/xxxxxxxx      │
 └─────────────────────────────────────────┘
   （リンクのIDだけでも入力できます）
```

### 2.3 処理と応答（すべて ephemeral）

| 状況 | 応答 |
|---|---|
| 処理中 | `⏳ リンクを確認しています…`（`defer(ephemeral=True)`） |
| 成功 | `✅ チャージ完了` / 受取額・反映後残高・送金者名 |
| 請求リンク | `❌ 請求リンクは受け取れません。送金リンクを作成してください` |
| 処理済み | `❌ このリンクは既に使用されています` |
| 金額範囲外 | `❌ チャージ額は ¥100 〜 ¥50,000 の範囲で指定してください` |
| 残高差分が不一致 | `⚠️ 確認中です。管理者が対応しますのでお待ちください`＋管理者へ通知 |
| Kyash口座なし/全停止 | `❌ ただいまチャージを受け付けできません` ＋管理者へ通知 |

処理手順は `docs/03` §3.1 を厳密に守ること（**受取成功 → 残高検証 → 記帳** の順序）。

## 3. 注文フロー

### 3.1 「📋 注文コード(HEX)を貼る」→ 入力 Modal

```
タイトル: 🍔 注文する
 ┌ 注文コード（HEX） ──────────────────────┐
 │                                         │  ← 複数行・必須
 └─────────────────────────────────────────┘
```

### 3.2 プレビューパネル（ephemeral）

hex をデコードして内容を提示し、ここで**受取方法を選ばせる**（R-2）。
このパネルが開いた瞬間に**投機的先読み**を開始する（`docs/04` §5.3）。

```
┌─────────────────────────────────────────────┐
│ 🍔 注文内容の確認                             │
│                                             │
│ 🏪 店舗       代々木店 (10528)                │
│ 🧾 商品数     3 点                            │
│ 💴 定価       ¥590                           │
│                                             │
│ 👤 あなたの負担率   60%  （負担 40% 適用中）    │
│ 💴 お支払い額       ¥354                      │
│ 👛 チャージ残高     ¥630 → ¥276               │
│                                             │
│ 📍 受取方法を選んでから確定してください          │
└─────────────────────────────────────────────┘
  [ 📍 受取方法を選択 ▼ ]
  [ ✅ 注文を確定する ]  [ ❌ キャンセル ]
```

- **受取方法セレクト**: `店内でお召し上がり` / `お持ち帰り` / `席までお届け` / `デリバリー`
  （表示名は `config.PICKUP_METHODS` が唯一の出どころ。実物のアプリに合わせてある）
  ⚠️ V-1 は解決済み（`docs/01` §11）。店内でお召し上がり／お持ち帰りはどちらも使える。
  その店・その時間に使えない受取方法は、そもそも選択肢に出さない
- 受取方法が未選択の間は「注文を確定する」を `disabled`
- 残高不足なら確定ボタンを `disabled` にし、`[ 🔗 チャージする ]` を出す
- パネルの `timeout` は 120 秒。失効時は「時間切れです。もう一度お試しください」に置換
- 確定ボタンの `custom_id` に **`idempotency_key`（UUID）** を埋め込む（`docs/04` §4.1-4）

### 3.3 進捗パネル（同一メッセージを編集し続ける）

無言の待ち時間を作らない。**これが「超高性能」の体感を最も左右する。**

```
⏳ 注文を処理しています…

✅ ① 残高を確保しました            ¥354
✅ ② 店舗を確認しました            代々木店
🔄 ③ マクドナルドへ送信しています…
⬜ ④ 注文番号を取得
```

各段階の完了時に `interaction.edit_original_response()` で更新する。

### 3.4 完了（ephemeral）

```
✅ 注文が完了しました
　 詳細と控えを DM にお送りしました。
```

DM が送れない場合（DM拒否設定）:

```
⚠️ 注文は完了しましたが DM を送信できませんでした
　 注文番号: 7161
　 DM の受信を許可してから、もう一度お試しください。
```

→ この場合も**注文自体は成立している**ため、注文番号を必ずその場に表示すること。

## 3.4 店舗の選び方（店名検索）

店舗IDを覚えている利用者はいないため、**店名の一部**で探せるようにする。

```
🏪 注文するお店を選んでください

店名の一部を入れるだけで探せます。
例）南砂　所沢　AKIBA　イオン

[🔍 店名でさがす] [🔢 店舗IDで指定]
[最近よく使われているお店 ▼]
```

### 検索の仕様

マクドナルドには店舗一覧のAPIが無いため、あらかじめ作った一覧
（`assets/stores.json` / **3,036店舗・全47都道府県**）を同梱して検索に使う。
一覧は**定期同期で自動更新**される（下記「一覧の更新」）。

> #### 店舗IDの規則（実測）
> 店舗IDは **JIS都道府県コード×1000 の5桁ゼロ埋め**。
>
> | 例 | 店舗 |
> |---|---|
> | `01003` | 西町店（北海道 = 01） |
> | `13934` | 南砂町店（東京都 = 13） |
> | `47527` | 那覇メインプレイス店（沖縄県 = 47） |
>
> **北海道〜栃木（01〜09）は先頭が 0 になる。**
> 整数として扱うと `01003` が `1003` になり、この9都道府県を丸ごと
> 取りこぼす。文字列のまま扱うこと。
> 利用者が先頭の 0 を省いて入力した場合は、ゼロ埋めしても探す
> （`store_index.get`）。

**照合前に文字をそろえる**（`store_index.normalize`）:

| 処理 | 例 |
|---|---|
| NFKC 正規化 | `ＡＫＩＢＡ` → `akiba` |
| ひらがな → カタカナ | `びっくかめら` → `ビックカメラ` |
| 空白・中黒・長音の除去 | `さくらもーる` ＝ `さくらモール` |

**並び順**: 店名が完全一致 → 前方一致 → 部分一致 → 住所に含まれる → ID一致。
同点なら名前の短い方を上に出す。

### 一覧の更新（自動）

新店舗の開店・閉店・店名変更・モバイルオーダー対応の切り替えを
自動で反映する（`services/mcd/store_sync.py`）。

| 間隔 | 内容 | 通信量 |
|---|---|---|
| **15分**（`STORE_INDEX_SYNC_MINUTES`） | 確認が古い店舗から400件ずつ取り直す。全3,036店舗を**約2時間で一周** | ETagが効くので大半は304（0バイト） |
| **60分**（`STORE_SITEMAP_CHECK_MINUTES`） | 公式の店舗検索サイトのサイトマップと照合し、店舗IDの増減を調べる | 約0.5MB |

- 書き出し先は `data/stores.json`。同梱の `assets/stores.json` より**優先して読む**
- 一時ファイルに書いてから差し替えるので、途中で落ちても壊れた一覧が残らない
- 変化があれば管理者チャンネルへ通知（開店・閉店・改名・モバイルオーダー可否）
- サイトマップに載っているが配信元に無いID（閉店直後など）は**24時間あけて再挑戦**
- サイトマップの取得に失敗しても、巡回更新は続行する
- 取得できなかった店舗を一覧から消すことはしない（一時的な通信失敗で消さないため）

### 一覧が無い場合

`assets/stores.json` が無くても動く。

- 過去に使った店舗（`store_cache`）からは検索できる
- 店舗IDを直接入力すれば常に注文できる
- `/store reindex` で一覧を作り直せる（**3〜5分**）

### 見つからなかったときの案内

店名は漢字で登録されているため、ひらがなのまま入力すると当たらない
（`まえばし` → 0件）。これが最も多い外れ方なので、案内文では
**漢字での入力を最初に**案内する。

- 漢字で入力（`まえばし` → `前橋`）
- 店名の一部だけ（`南砂` `所沢` `イオン`）
- 市区町村・都道府県（`江東区` `群馬県`）
- 店舗IDで指定

### 価格の見せ方

値段が違うのはデリバリーだけ（202/247商品）。

違うときだけ2行に分ける。同じ金額を2行並べても読みにくいだけ。

> ⚠️ その受取方法の価格が欠けていたら、他の価格で代える。
> **¥0 と表示するのが一番まずい**（`Product.price_for`）。

## 3.4.6 お受け取り方法は最後に聞く（PickupView）

### なぜ最後か

中身が決まる前に受取方法を選ばせると、商品を足すたびに
関係のない選択肢が目に入って迷う。実物のアプリと同じく、

- その店で使える受取方法だけを出す（`StoreInfo.delivery_methods` と時間帯）
- 前回と同じ受取方法を緑（success）で目立たせる

カタログから引き直す。

> ⚠️ ここを忘れると、受取方法と違う金額で注文コードを作ってしまう。
> 負担率の計算も狂う。

> **見た目を通常の実績と一切変えないこと。**

> 「代理」と分かる印を付けない。

- 誰が代理送信したかは**サーバーのログにだけ**記録する（埋め込みには出さない）

> 埋め込みを1フィールドずつ比較する自動テスト（`tests/test_achievement.py`）で、
> 通常の実績と完全一致することを検証している。

## 5.4 更新情報の送り先を分ける

|---|---|---|

**送り先を1つも設定していなければ何も送らない。**

## 5.5 残高の増減パネル

### 目的

共有の財布なので、**誰がいくら使ったか**が見えているほうが分かりやすい。
注文の操作そのものは本人にしか見えないが、残高が動いた事実は共有する。

### 送り先の決め方（この順）

1. `channel_balance` が設定されていれば、そのチャンネル
2. 設定が無ければ、**操作したチャンネル**（既定。利用者の求めた挙動）
3. DM・グループDM・サーバー外なら**何もしない**
   （「誰にでも見える」が成り立たないため）

`channel_balance` が消えたチャンネルを指している場合は 2 に落とす。

### 表示項目（`/config balance_panel`）

| 項目 | 既定 | 内容 |
|---|---|---|
| `name`（ご利用者名） | ✅ ON | OFF にすると匿名コード（`U-7F3A`）になる |
| `amount`（増減額） | ✅ ON | `+¥3,000` / `-¥480` |
| `balance`（残高） | ❌ **OFF** | **いくら持っているかは最も知られたくない情報** |
| `reason`（内容） | ✅ ON | 「Kyash でチャージ」「マクドナルドの注文（南砂町店）」 |
| `orders`（利用回数） | ❌ OFF | 通算の注文件数 |

`enabled:False` でパネル自体を出さなくできる。

### 出す場面

| 場面 | 符号 | 理由の文言 |
|---|---|---|
| チャージ完了 | ＋ | `Kyash でチャージ` |
| 注文成立 | − | `マクドナルドの注文（店舗名）` |
| `/admin grant` | ±  | `管理者による調整：<理由>` |

`/admin grant` では**対象の利用者名**で出す（操作した管理者ではない）。

> 手動レビューの解決（`/admin review` → 返金・確定）では出さない。
> 対応する増減パネルが出ていない注文なので、返金だけが出ると読み手が混乱する。
> 記録は監査ログ（`audit_log`）に残る。

### 実装上の絶対条件

> **このパネルは飾りである。注文やチャージを絶対に止めない。**

`ui/balance_panel.post()` は内部で全例外を受け止めて `False` を返す。
権限不足・送り先の消失・設定の破損で注文が失敗したら本末転倒。

```python
try:
    return await _post(...)
except Exception:
    log.exception("残高パネルの処理で予期しないエラー")
    return False
```

送信前に `permissions_for()` で `send_messages` と `embed_links` を確かめる。
例外で気づくより静かで速い。判定できない環境では止めない。

## 5.6 注文番号ページ（services/web.py）

店頭で注文番号を見せるためだけのページ。BOT と同じプロセスで
aiohttp を動かす（discord.py が持っているので追加導入は不要）。

### URLの作り

```
https://example.com/order/<view_token>
```

`view_token` は `secrets.token_urlsafe(16)`（128ビット）。
注文番号が決まった時点で `core/saga.py` が1回だけ作り、以後変えない。

> ⚠️ **注文番号そのものをURLにしてはいけない。**
> 4桁しかないので、0000〜9999 を順に試すだけで他人の注文が覗ける。

### 出す情報

| 出す | 出さない |
|---|---|
| 注文番号・店舗名・受取方法・注文時刻 | 金額・負担率・誰が頼んだか |

### 付けているヘッダ

`X-Robots-Tag: noindex` / `Cache-Control: no-store` /
`Referrer-Policy: no-referrer` / `X-Content-Type-Options: nosniff`

### 期限

`receipt_page_hours`（既定12時間）を過ぎたら「見つかりません」を返す。
注文番号は当日しか使わないので、長くは残さない。0で期限なし。

> ⚠️ このページが落ちても注文には影響しない。
> 注文番号は DM の控えにも入っている。起動に失敗してもBOTは動かす。

## 5.7 招待キャンペーン（core/invite.py）

残高を配る＝**実際にお金が出ていく**。歯止めを重ねてある。

| # | 歯止め | 実装 |
|---|---|---|
| 1 | 既定で無効 | `invite_enabled = False` |
| 2 | 1人あたりの上限 | `invite_max_per_user` |
| 3 | 全体の予算 | `invite_budget` |
| 4 | 1人は一度しか招待されない | `invites.discord_id` が主キー |
| 5 | 自作自演の禁止 | `link()` で自分自身を弾く |
| 6 | 条件を満たすまで渡さない | 既定 `first_order` |
| 7 | 出どころが残る | `core/ledger.adjust` を通す |

### 渡す順番

```
link()            紐づけるだけ。特典は渡さない
  ↓
grant_if_ready()  条件を満たしていれば渡す
   1. 予算を確認
   2. 元帳に記帳（ここでお金が動く）
   3. invites.rewarded = True を立てる
```

> ⚠️ **記帳してから記録を立てる。** 逆にすると、記帳に失敗したときに
> 「渡していないのに渡したことになる」。何度呼んでも二重には渡らない。

### 招待の紐づけ方

| 方式 | 必要なもの | 取り違え |
|---|---|---|
| コードを本人が入力 | なし | 起きない |
| Discordの招待を自動追跡 | SERVER MEMBERS INTENT | 同時入室で起こりうる |

自動追跡は、入室の前後で各招待リンクの使用回数を見比べて、
増えた1本を探す。増えたものが**ちょうど1本でなければ紐づけない**
（0本＝権限なし／2本以上＝同時入室）。
間違った人に特典を渡すより、渡さないほうがまだよい。

### 招待コード

`code_for()` が discord_id の SHA-256 から6文字を作る。いつでも同じ値。

使う文字: `23456789ABCDEFGHJKMNPQRSTUVWXYZ`
> ⚠️ `0 O` と `1 I L` は入れない。読み上げたり書き写したりするとき、
> フォントによってほぼ同じに見える。


- `jwtMfaToken` の有効期間は短いため、**1つ目の Modal 送信から続けて2つ目を開く**
- OTP を3回間違えたら中断し、最初からやり直させる
- 登録直後にヘルスチェックを1回実行し、失敗したら `DEGRADED` で登録する

### 6.2 `/kyash add`

```
Modal「🔑 Kyashアカウントを追加」
 ┌ 表示名（任意） ─────────┐
 ┌ メールアドレス ─────────┐
 ┌ パスワード ────────────┐

   ↓ Kyash(email, password) → SMS送信

Modal「🔑 認証コードの入力」
 ┌ SMSで届いた6桁 ────────┐

   ↓ login(otp)
   ↓ access_token / client_uuid / installation_uuid を暗号化保存
   ↓ get_profile() → is_kyc / get_wallet() → 残高
✅ 登録完了（ephemeral）
```

⚠️ `client_uuid` と `installation_uuid` は**2つで1セット**。
これを保存しておけば以後の再ログインで OTP が不要になる（`docs/03` §2.1）。**必ず両方保存すること。**

すべて ephemeral で返し、**利用者に次の行動を示す**。

| 残高不足 | `❌ 残高が不足しています\n必要 ¥354 / 現在 ¥120` ＋ `[ 🔗 チャージする ]` |
