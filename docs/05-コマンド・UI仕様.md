# 05. コマンド・UI 仕様書

> 絵文字は `emoji.py` の定数のみを使う（`docs/04` §9）。カスタム絵文字は使用しない。
> 全コマンドは `app_commands`（スラッシュ）で実装する。`hybrid_command` は使わない（`docs/04` §8）。

---

## 0. 操作方式の原則 ★最重要

| 対象 | 操作方式 |
|---|---|
| **管理者** | **スラッシュコマンド** ＋ **管理者パネル** |
| **利用者** | ⚠️ **パネルとボタンのみ**（サーバー設定でスラッシュコマンドが使えないため） |

### 0.1 利用者向けスラッシュコマンドは一切作らない

**利用者が使う機能は、すべて常設パネルのボタンから始まる。**
`/order` `/balance` `/charge` のような利用者向けコマンドは**実装しない**。

### 0.2 二層ビュー構成

```
【常設パネル】 timeout=None / custom_id 固定 / bot.add_view() で復元
     チャンネルに貼りっぱなし。再起動しても動く。誰が押してもよい。
          │  ボタン押下
          ▼
【一時ビュー】 timeout=120秒 / ephemeral / 押した本人にだけ見える
     カート編集・受取方法選択・確定。状態はDBに保存する。
```

- **常設パネルの View には状態を持たせない。** 再起動で消えるため
- カート等の状態は **DB に `discord_id` をキーに保存**し、一時ビューはそれを読む
- 一時ビューは**押した本人以外の操作を弾く**（`interaction.user.id` を照合）

### 0.3 常設パネルの実装規約

#### 貼ってあるパネルは自動で最新にする

再起動すると `add_view()` でボタンは**反応するように戻る**。
しかしチャンネルに貼ってあるメッセージの中身（embed とボタンの並び）は
Discord 側に保存されたままなので、**古い内容が残り続ける**。

新しいボタンを足しても、貼り直すか `/panel refresh` を叩くまで
利用者には出てこない。管理者がそれを毎回覚えておくのは無理なので、
`main.on_ready` → `_refresh_panels()` が起動のたびに自動で合わせる。

- 更新処理は `cogs/panel.refresh_all(bot)` の1か所だけ
  （コマンドと起動時で別々に書くと、片方を直し忘れて食い違う）
- ⚠️ ここで何が起きても**起動を止めない**。
  チャンネルが消えていても、例外が出ても、ログに残して先へ進む


```python
class ChargePanel(discord.ui.View):
    def __init__(self):
        super().__init__(timeout=None)          # ★必須

    @discord.ui.button(label="チャージする", emoji="🔗",
                       style=discord.ButtonStyle.primary,
                       custom_id="panel:charge:start")   # ★固定IDが必須
    async def charge(self, itx, button): ...

# main.py の setup_hook で必ず登録する（これが無いと再起動後ボタンが死ぬ）
self.add_view(ChargePanel())
```

> ⚠️ `custom_id` は**永久に変えない**。変えると既に貼ってあるパネルのボタンが反応しなくなる。
> 命名規則: `panel:<パネル名>:<動作>`

## 1.4 注文方式の切り替え

`/config order_mode` で、利用者が使える注文方法を制限できる。

| 値 | 注文の入口 | 「注文コードを作る」ボタン |
|---|---|---|
| `both`（既定） | 方法を選ぶ画面を出す | 表示する |
| `hex` | **直接 HEX 入力モーダル**を開く | 表示する |
| `menu` | **直接 店舗選択**へ進む | **非表示** |

### 実装上の注意

常設パネルは `add_view()` で**全ボタンを登録**し、表示だけを出し分ける。
ボタンを登録から外すと、設定変更前に貼ったパネルのボタンが反応しなくなるため。

```python
OrderPanel(mode=None)    # 復元用: 全ボタンを登録
OrderPanel(mode="menu")  # 設置用: HEXボタンを外して表示
```

非表示のボタンが押された場合（古いパネルなど）は、その旨を案内して終わる。

```
┌─────────────────────────────────────────────┐

│                                             │
│ 🟢 稼働中 ／ マクドナルド 3件 ／ Kyash 2件      │

```

| ボタン | custom_id | 動作 |
|---|---|---|
| 📊 統計 | `panel:admin:stats` | 注文数・成功率・GMV・負担総額・元帳整合性 |
| 💴 負担率 | `panel:admin:subsidy` | 負担率ルールの一覧・追加・削除 |

## 2. チャージフロー

### 2.1 チャージパネル（常設・指定チャンネル）

```
┌─────────────────────────────────────────────┐
│ 💴 残高チャージ                               │
│                                             │
│ Kyash の送金リンクで残高をチャージできます。    │
│                                             │
│ ▸ Kyash アプリで「送金リンク」を作成          │
│ ▸ 下のボタンからリンクを貼り付け              │
│ ▸ 受け取りが完了すると即座に残高へ反映されます  │
│                                             │
│ ℹ️ 1回のチャージは ¥100 〜 ¥50,000 です       │
│ ⚠️ 請求リンクは受け付けできません              │
│ ⚠️ チャージした残高の払い戻しはできません      │
└─────────────────────────────────────────────┘
   [ 🔗 チャージする ]   [ 👛 残高を確認 ]
```

- `View` は `timeout=None` の永続ビュー。`custom_id` を固定し、`setup_hook` で `add_view()` する
- 再起動後もボタンが生き続けるようにすること

### 2.2 チャージ Modal

```
タイトル: 💴 残高チャージ
 ┌ Kyash 送金リンク ───────────────────────┐
 │ https://kyash.me/payments/xxxxxxxx      │
 └─────────────────────────────────────────┘
   （リンクのIDだけでも入力できます）
```

### 2.3 処理と応答（すべて ephemeral）

| 状況 | 応答 |
|---|---|
| 処理中 | `⏳ リンクを確認しています…`（`defer(ephemeral=True)`） |
| 成功 | `✅ チャージ完了` / 受取額・反映後残高・送金者名 |
| 請求リンク | `❌ 請求リンクは受け取れません。送金リンクを作成してください` |
| 処理済み | `❌ このリンクは既に使用されています` |
| 金額範囲外 | `❌ チャージ額は ¥100 〜 ¥50,000 の範囲で指定してください` |
| 残高差分が不一致 | `⚠️ 確認中です。管理者が対応しますのでお待ちください`＋管理者へ通知 |
| Kyash口座なし/全停止 | `❌ ただいまチャージを受け付けできません` ＋管理者へ通知 |

処理手順は `docs/03` §3.1 を厳密に守ること（**受取成功 → 残高検証 → 記帳** の順序）。

## 3. 注文フロー

### 3.1 「📋 注文コード(HEX)を貼る」→ 入力 Modal

```
タイトル: 🍔 注文する
 ┌ 注文コード（HEX） ──────────────────────┐
 │                                         │  ← 複数行・必須
 └─────────────────────────────────────────┘
```

### 3.2 プレビューパネル（ephemeral）

hex をデコードして内容を提示し、ここで**受取方法を選ばせる**（R-2）。
このパネルが開いた瞬間に**投機的先読み**を開始する（`docs/04` §5.3）。

```
┌─────────────────────────────────────────────┐
│ 🍔 注文内容の確認                             │
│                                             │
│ 🏪 店舗       代々木店 (10528)                │
│ 🧾 商品数     3 点                            │
│ 💴 定価       ¥590                           │
│                                             │
│ 👤 あなたの負担率   60%  （負担 40% 適用中）    │
│ 💴 お支払い額       ¥354                      │
│ 👛 チャージ残高     ¥630 → ¥276               │
│                                             │
│ 📍 受取方法を選んでから確定してください          │
└─────────────────────────────────────────────┘
  [ 📍 受取方法を選択 ▼ ]
  [ ✅ 注文を確定する ]  [ ❌ キャンセル ]
```

- **受取方法セレクト**: `店内でお召し上がり` / `お持ち帰り` / `席までお届け` / `デリバリー`
  （表示名は `config.PICKUP_METHODS` が唯一の出どころ。実物のアプリに合わせてある）
  ⚠️ V-1 は解決済み（`docs/01` §11）。店内でお召し上がり／お持ち帰りはどちらも使える。
  その店・その時間に使えない受取方法は、そもそも選択肢に出さない
- 受取方法が未選択の間は「注文を確定する」を `disabled`
- 残高不足なら確定ボタンを `disabled` にし、`[ 🔗 チャージする ]` を出す
- パネルの `timeout` は 120 秒。失効時は「時間切れです。もう一度お試しください」に置換
- 確定ボタンの `custom_id` に **`idempotency_key`（UUID）** を埋め込む（`docs/04` §4.1-4）

### 3.3 進捗パネル（同一メッセージを編集し続ける）

無言の待ち時間を作らない。**これが「超高性能」の体感を最も左右する。**

```
⏳ 注文を処理しています…

✅ ① 残高を確保しました            ¥354
✅ ② 店舗を確認しました            代々木店
🔄 ③ マクドナルドへ送信しています…
⬜ ④ 注文番号を取得
```

各段階の完了時に `interaction.edit_original_response()` で更新する。

### 3.4 完了（ephemeral）

```
✅ 注文が完了しました
　 詳細と控えを DM にお送りしました。
```

DM が送れない場合（DM拒否設定）:

```
⚠️ 注文は完了しましたが DM を送信できませんでした
　 注文番号: 7161
　 DM の受信を許可してから、もう一度お試しください。
```

→ この場合も**注文自体は成立している**ため、注文番号を必ずその場に表示すること。

## 3.4 店舗の選び方（店名検索）

店舗IDを覚えている利用者はいないため、**店名の一部**で探せるようにする。

```
🏪 注文するお店を選んでください

店名の一部を入れるだけで探せます。
例）南砂　所沢　AKIBA　イオン

[🔍 店名でさがす] [🔢 店舗IDで指定]
[最近よく使われているお店 ▼]
```

### 検索の仕様

マクドナルドには店舗一覧のAPIが無いため、あらかじめ作った一覧
（`assets/stores.json` / **3,036店舗・全47都道府県**）を同梱して検索に使う。
一覧は**定期同期で自動更新**される（下記「一覧の更新」）。

> #### 店舗IDの規則（実測）
> 店舗IDは **JIS都道府県コード×1000 の5桁ゼロ埋め**。
>
> | 例 | 店舗 |
> |---|---|
> | `01003` | 西町店（北海道 = 01） |
> | `13934` | 南砂町店（東京都 = 13） |
> | `47527` | 那覇メインプレイス店（沖縄県 = 47） |
>
> **北海道〜栃木（01〜09）は先頭が 0 になる。**
> 整数として扱うと `01003` が `1003` になり、この9都道府県を丸ごと
> 取りこぼす。文字列のまま扱うこと。
> 利用者が先頭の 0 を省いて入力した場合は、ゼロ埋めしても探す
> （`store_index.get`）。

**照合前に文字をそろえる**（`store_index.normalize`）:

| 処理 | 例 |
|---|---|
| NFKC 正規化 | `ＡＫＩＢＡ` → `akiba` |
| ひらがな → カタカナ | `びっくかめら` → `ビックカメラ` |
| 空白・中黒・長音の除去 | `さくらもーる` ＝ `さくらモール` |

**並び順**: 店名が完全一致 → 前方一致 → 部分一致 → 住所に含まれる → ID一致。
同点なら名前の短い方を上に出す。

### 一覧の更新（自動）

新店舗の開店・閉店・店名変更・モバイルオーダー対応の切り替えを
自動で反映する（`services/mcd/store_sync.py`）。

| 間隔 | 内容 | 通信量 |
|---|---|---|
| **15分**（`STORE_INDEX_SYNC_MINUTES`） | 確認が古い店舗から400件ずつ取り直す。全3,036店舗を**約2時間で一周** | ETagが効くので大半は304（0バイト） |
| **60分**（`STORE_SITEMAP_CHECK_MINUTES`） | 公式の店舗検索サイトのサイトマップと照合し、店舗IDの増減を調べる | 約0.5MB |

- 書き出し先は `data/stores.json`。同梱の `assets/stores.json` より**優先して読む**
- 一時ファイルに書いてから差し替えるので、途中で落ちても壊れた一覧が残らない
- 変化があれば管理者チャンネルへ通知（開店・閉店・改名・モバイルオーダー可否）
- サイトマップに載っているが配信元に無いID（閉店直後など）は**24時間あけて再挑戦**
- サイトマップの取得に失敗しても、巡回更新は続行する
- 取得できなかった店舗を一覧から消すことはしない（一時的な通信失敗で消さないため）

### 一覧が無い場合

`assets/stores.json` が無くても動く。

- 過去に使った店舗（`store_cache`）からは検索できる
- 店舗IDを直接入力すれば常に注文できる
- `/store reindex` で一覧を作り直せる（**3〜5分**）

### 見つからなかったときの案内

店名は漢字で登録されているため、ひらがなのまま入力すると当たらない
（`まえばし` → 0件）。これが最も多い外れ方なので、案内文では
**漢字での入力を最初に**案内する。

- 漢字で入力（`まえばし` → `前橋`）
- 店名の一部だけ（`南砂` `所沢` `イオン`）
- 市区町村・都道府県（`江東区` `群馬県`）
- 店舗IDで指定

違うときだけ2行に分ける。同じ金額を2行並べても読みにくいだけ。

> ⚠️ その受取方法の価格が欠けていたら、他の価格で代える。
> **¥0 と表示するのが一番まずい**（`Product.price_for`）。

## 3.4.6 お受け取り方法は最後に聞く（PickupView）

### なぜ最後か

中身が決まる前に受取方法を選ばせると、商品を足すたびに
関係のない選択肢が目に入って迷う。実物のアプリと同じく、

- その店で使える受取方法だけを出す（`StoreInfo.delivery_methods` と時間帯）

カタログから引き直す。

> ⚠️ ここを忘れると、受取方法と違う金額で注文コードを作ってしまう。
> 負担率の計算も狂う。

> **見た目を通常の実績と一切変えないこと。**

> 「代理」と分かる印を付けない。

- 誰が代理送信したかは**サーバーのログにだけ**記録する（埋め込みには出さない）

> 埋め込みを1フィールドずつ比較する自動テスト（`tests/test_achievement.py`）で、
> 通常の実績と完全一致することを検証している。

## 5.5 残高の増減パネル

### 目的

共有の財布なので、**誰がいくら使ったか**が見えているほうが分かりやすい。
注文の操作そのものは本人にしか見えないが、残高が動いた事実は共有する。

### 送り先の決め方（この順）

1. `channel_balance` が設定されていれば、そのチャンネル
2. 設定が無ければ、**操作したチャンネル**（既定。利用者の求めた挙動）
3. DM・グループDM・サーバー外なら**何もしない**
   （「誰にでも見える」が成り立たないため）

`channel_balance` が消えたチャンネルを指している場合は 2 に落とす。

### 表示項目（`/config balance_panel`）

| 項目 | 既定 | 内容 |
|---|---|---|
| `name`（ご利用者名） | ✅ ON | OFF にすると匿名コード（`U-7F3A`）になる |
| `amount`（増減額） | ✅ ON | `+¥3,000` / `-¥480` |
| `balance`（残高） | ❌ **OFF** | **いくら持っているかは最も知られたくない情報** |
| `reason`（内容） | ✅ ON | 「Kyash でチャージ」「マクドナルドの注文（南砂町店）」 |
| `orders`（利用回数） | ❌ OFF | 通算の注文件数 |

`enabled:False` でパネル自体を出さなくできる。

### 出す場面

| 場面 | 出すか |
|---|---|
| `/admin grant`（管理者が手で動かす） | ✅ 出す |
| チャージ完了 | ❌ 出さない |
| 注文成立 | ❌ 出さない |

> ⚠️ 利用者が自分で使ったぶんまで公開されるのは望まれていない。
> 出すのは**管理者が手で動かしたときだけ**。お金を動かした記録が
> 人目に触れる形で残るようにするため。

`/admin grant` では**対象の利用者名**で出す（操作した管理者ではない）。

> 手動レビューの解決（`/admin review` → 返金・確定）では出さない。
> 対応する増減パネルが出ていない注文なので、返金だけが出ると読み手が混乱する。
> 記録は監査ログ（`audit_log`）に残る。

### 実装上の絶対条件

> **このパネルは飾りである。注文やチャージを絶対に止めない。**

`ui/balance_panel.post()` は内部で全例外を受け止めて `False` を返す。
権限不足・送り先の消失・設定の破損で注文が失敗したら本末転倒。

```python
try:
    return await _post(...)
except Exception:
    log.exception("残高パネルの処理で予期しないエラー")
    return False
```

送信前に `permissions_for()` で `send_messages` と `embed_links` を確かめる。
例外で気づくより静かで速い。判定できない環境では止めない。

## 5.6 注文番号ページ（services/web.py）

店頭で注文番号を見せるためだけのページ。BOT と同じプロセスで
aiohttp を動かす（discord.py が持っているので追加導入は不要）。

### URLの作り

```
https://example.com/order/<view_token>
```

`view_token` は `secrets.token_urlsafe(16)`（128ビット）。
注文番号が決まった時点で `core/saga.py` が1回だけ作り、以後変えない。

> ⚠️ **注文番号そのものをURLにしてはいけない。**
> 4桁しかないので、0000〜9999 を順に試すだけで他人の注文が覗ける。

### 出す情報

| 出す | 出さない |
|---|---|
| 注文番号・店舗名・受取方法・注文時刻 | 金額・負担率・誰が頼んだか |

### 付けているヘッダ

`X-Robots-Tag: noindex` / `Cache-Control: no-store` /
`Referrer-Policy: no-referrer` / `X-Content-Type-Options: nosniff`

### 期限

`receipt_page_hours`（既定12時間）を過ぎたら「見つかりません」を返す。
注文番号は当日しか使わないので、長くは残さない。0で期限なし。

> ⚠️ このページが落ちても注文には影響しない。
> 注文番号は DM の控えにも入っている。起動に失敗してもBOTは動かす。

## 5.7 招待キャンペーン（core/invite.py）

残高を配る＝**実際にお金が出ていく**。歯止めを重ねてある。

| # | 歯止め | 実装 |
|---|---|---|
| 1 | 既定で無効 | `invite_enabled = False` |
| 2 | 1人あたりの上限 | `invite_max_per_user` |
| 3 | 全体の予算 | `invite_budget` |
| 4 | 1人は一度しか招待されない | `invites.discord_id` が主キー |
| 5 | 自作自演の禁止 | `link()` で自分自身を弾く |
| 6 | 条件を満たすまで渡さない | 既定 `first_order` |
| 7 | 出どころが残る | `core/ledger.adjust` を通す |

### 渡す順番

```
link()            紐づけるだけ。特典は渡さない
  ↓
grant_if_ready()  条件を満たしていれば渡す
   1. 予算を確認
   2. 元帳に記帳（ここでお金が動く）
   3. invites.rewarded = True を立てる
```

> ⚠️ **記帳してから記録を立てる。** 逆にすると、記帳に失敗したときに
> 「渡していないのに渡したことになる」。何度呼んでも二重には渡らない。

### 招待の紐づけ方

| 方式 | 必要なもの | 取り違え |
|---|---|---|
| コードを本人が入力 | なし | 起きない |
| Discordの招待を自動追跡 | SERVER MEMBERS INTENT | 同時入室で起こりうる |

自動追跡は、入室の前後で各招待リンクの使用回数を見比べて、
増えた1本を探す。増えたものが**ちょうど1本でなければ紐づけない**
（0本＝権限なし／2本以上＝同時入室）。
間違った人に特典を渡すより、渡さないほうがまだよい。

### 招待コード

`code_for()` が discord_id の SHA-256 から6文字を作る。いつでも同じ値。

使う文字: `23456789ABCDEFGHJKMNPQRSTUVWXYZ`
> ⚠️ `0 O` と `1 I L` は入れない。読み上げたり書き写したりするとき、
> フォントによってほぼ同じに見える。

## 5.8 セットの選択枠に入れられる商品（services/mcd/slot_rules.py）

### カタログには書かれていない

menu.json の `choices` が持つのは `referenceProduct` と `defaultProduct`
だけで、「その枠に何を入れられるか」の一覧はどこにも無い。

2026-10 時点で以下を全て確認し、どれにも無いことを確かめた:

`choices` の各項目 / `grills` / `relatedSets` / `collections` /
`sizeVariants` / `canAdds` / `limitedAbility` / `groupMenu`（kind・setType・
tNotes を含む）/ `valueLunchCollection` / `employeeMealCollection`

そのため候補は「参照商品が属するカテゴリ全体」から出している。
**この中にはその枠に入れられないものが混ざる。**
例: サイドメニューには ¥50 のソース類（ナゲットの付属品）が入っているが、
セットのサイドとしては選べない。

### 決め打ちで消さない

どれがダメかを手で書くと、こちらの思い込みで選べるはずのものまで
消えてしまう（以前「ドリンクがコーラしか選べない」状態になった原因）。
代わりに**実際に断られた組み合わせを覚えて、次から出さない**。

```
注文が断られる
  ↓
learn_rejected_choices()        ui/flows.py
  ↓
slot_rules.reject(店舗, 枠, 商品)
  ↓
choice_candidates() が次から外す
```

> ⚠️ **本当の時間外と取り違えないこと。**
> マクドナルドは組み合わせが悪いときも「ただいまのお時間は
> 選択した商品のお取り扱いがありません」と返してくる。
> **こちらの時間判定が通っていたのに**そう言われた場合**だけ**、
> 組み合わせの問題として記録する。

> ⚠️ 一度通った組み合わせは覚え直さない。売り切れなど、その時だけの
> 事情で断られることがある。

### 利用者への説明

組み合わせが原因と分かったときは、「時間外です」ではなく
「この組み合わせは選べませんでした」と伝える。
そのまま伝えると、待てば直ると誤解させてしまう。

### 並び順

確実に選べると分かっているのは**参照商品とそのサイズ違い**だけなので、
それを先頭に並べる。上から選ぶほど通りやすくなる。

### 管理

`/config slot_rules` で件数を確認、`forget_store:<店舗ID>` で取り消し。
保存先は `data/slot_rules.json`。

## 5.9 注文を送る前に止めること

「表示したのに注文できない」が利用者にとって一番つらい。
断られてから気づく経路を、段階的に塞ぐ。

| # | どこで | 何を見るか |
|---|---|---|
| 1 | 商品一覧（`visible_products`） | 時間帯 **＋ 枠を埋められるか** |
| 2 | 商品の詳細（`ProductDetailView`） | 埋められないセットはボタンを押せなくし、理由を書く |
| 3 | カートに入れるとき（`OptionView._on_ok`） | 必須の枠が選ばれているか |
| 4 | 注文へ進むとき（`CartView._on_go`） | カートの中身が揃っているか・販売時間内か |
| 5 | 注文の登録のあと（`saga` ③） | **マクドナルドが言う金額と一致するか** |

### 埋めようがない枠

⚠️ ハッピーセットのように、参照商品がカタログの `products` に
**載っていない**枠や、参照が空の枠がある（実データで9商品）。
候補を1つも出せないのに必須なので、そのまま送ると断られる。
`ParsedMenu.unfillable_slots()` で見つけて、最初から出さない。

### 金額の食い違い（saga ③）

カタログは最大 `MENU_STALE_MINUTES` 分古いことがある。
値上げに気づかずに進むと、**利用者からは古い安い金額を取り、
カードには新しい高い金額が請求される**。差額は管理者が黙って被る。

`StoreOrder` は課金前（課金は ④ `AuthoriseOrder`）なので、
ここで止めれば1円も動かない。`PriceChanged` で中止し、
確保していた残高を戻す。

```python
if stored.total_amount and stored.total_amount != list_price:
    raise PriceChanged(list_price, stored.total_amount)
```

> ⚠️ 相手が金額を言ってこない（0）ときは止めない。
> 仕様が変わって全注文が止まるほうが困る。

> ⚠️ 金額の食い違いでアカウントの健全性を下げない。
> 値上げのたびにアカウントが止まってしまう。

## 5.10 選択枠に入る商品の決め方

カタログは枠の中身を**直接は教えてくれない**。3段階で手繰る。

### ① 枠そのものの参照

`choices[].defaultProduct` → `referenceProduct` の順に見る。

### ② 同じ枠コードを使う他の商品の参照

> ⚠️ チキンマックナゲット**5ピース**の枠 `7251` には参照が無い。
> 同じ枠を持つ**15ピース**には `6048` が入っている。
> 枠コードは商品をまたいで共通なので、他から借りてよい。

### ③ 名前で読み替える

> ⚠️ `6048`（バーベキューソース）は `products` に**無い**。
> 注文できるのは同じ名前の `5502`。
> `groupMenu` 側にしかない商品コードが参照に使われている。

### 候補の母集団と、価格帯での絞り込み

参照商品の属するカテゴリを母集団にする。カテゴリが引けなければ、
サイズ違いの仲間から引く（ポテトSは単体ではどのカテゴリにも無いが、
同じ群のポテトMはサイドメニューにいる）。

母集団には、その枠に入れられないものが混ざる。
**参照商品の値段の 0.3〜3.0 倍**に収まるものだけを残す。

| 枠 | 参照 | 絞り込みの効果 |
|---|---|---|
| ソース枠 7251 | バーベキューソース ¥50 | 17品 → **ソース3種だけ** |
| セットのサイド 9987009 | ポテトM ¥370 | 17品 → 14品（¥50のソースだけ除外）|
| セットのドリンク 9997918 | コーラM ¥310 | 24品 → **24品**（¥140のコーヒーも残る）|

> ⚠️ この倍率は実データの全枠を確認して決めた。
> 狭めるとコーヒーのような正しい選択肢が消える。

## 5.11 構成品が持つ選択枠（入れ子）

> ⚠️ **「食べくらべポテナゲ特大が注文できない」の原因。**

ポテナゲは、構成品（チキンマックナゲット）が**さらに選択枠**
（ソース）を持っている。実データで7商品。

```
食べくらべポテナゲ特大
 └ チキンマックナゲット5ピース ×2    ← composition
     └ 枠 7251                      ← この商品自身の choices
         └ バーベキューソース
```

これを送らないと必須の枠が空のまま注文することになり、断られる。

### 送り方

> ⚠️ **既定のままの構成品は送らない**のが原則だが、
> その構成品が選択枠を持つときは**送る**。
> 中に「選んだもの」を入れて渡す必要があるため。

`ParsedMenu.nested_choices()` が (構成品コード, 枠) を返す。
画面でもこの枠を聞き、`picks` には `"構成品コード/枠コード"` を鍵にして
記録する（上位の枠と混ざらないように）。

### 画面の見出し

枠コード（`9987009`）をそのまま出さない。利用者には何の枠か分からない。
`_slot_label()` が、カテゴリ名 → 候補の名前 の順に言い当てる。

## 5.12 選択肢専用の商品（6xxx番台）

> ⚠️ **`products` に載らない商品がある。**
> `groupMenu` と `limitedAbility` にだけ現れ、値段が 0 のもの。
> ナゲットに付けるソース、サイドサラダのドレッシング、
> シャカチキのシーズニング、ハッピーセットのおもちゃ。

### 同じ名前で別物がある

```
5502 バーベキューソース  price=50   ← 単品で買うソース（products にある）
6048 バーベキューソース  price=0    ← ナゲットに付ける無料のソース
```

> ⚠️ **名前が同じだからと `products` 側に読み替えてはいけない。**
> 無料のはずのソースを50円で注文することになる。
> 枠の参照（`6048`）はそのまま使う。

### どの枠に何が入るか

カタログは枠ごとの候補を持たないが、選択肢専用の商品は
**`kind` と `dayPart` の組で綺麗に分かれる**。

| グループ | 中身 | 使う枠 |
|---|---|---|
| `(KIND_NONE, BREAKFAST_REGULAR)` | 6048/6049/6059 ソース3種 | ナゲット 7251 |
| `(KIND_NONE, "")` | 6118 おもちゃ不要 ＋ おもちゃ4種 | ハッピーセット 9997008 |
| `(KIND_SIDE, REGULAR)` | 6042 シャカチキ シーズニング | シャカチキ 9997021 |
| `(KIND_SIDE, "")` | 6020 焙煎胡麻ドレッシング | サイドサラダ 9997136 |

参照のある枠はその商品のグループを使う。参照が無い枠は、
① 名前に親商品の名前が入るもの（「**シャカチキ** チェダーチーズ味…」）
② 親と同じ `kind`・`dayPart`
③ 親と同じ `kind` のうち、他に取られていないもの
の順に探す。

> ⚠️ 材料コード（`999xxx` ピクルス・氷）と社内用の符号（`【CLR】…`）は
> 候補に入れない。混ぜるとソースの枠に「氷」が並ぶ。

> ⚠️ 同じ商品の他の枠がすでに使っているグループは外す。
> ハッピーセットでおもちゃが2つの枠に出てしまう。

保存は `store_cache.menu_extras`（JSON配列）。
`products` に載らないので `menu_products` には入れられない。

### どうしても分からない枠

それでも解けない枠が残る（ハッピーセットのメインを選ぶ `9987016` など、
6商品）。候補を1つも出せないので、**その商品は一覧に出さない**。
空のまま送って断られるより、最初から出さないほうがよい。

## 6. アカウント追加フロー（R-8 / C-2）

### 6.1 `/mcd add`

```
Modal「🔑 マクドナルドアカウントを追加」
 ┌ 表示名（任意） ─────────┐
 ┌ メールアドレス ─────────┐
 ┌ パスワード ────────────┐      ← ⚠️ ephemeral。入力値は即暗号化し破棄

   ↓ login(email, password) → jwtMfaToken

Modal「🔑 認証コードの入力」
 ┌ SMS/メールで届いた6桁 ───┐

   ↓ login_with_mfa(mfa_token, otp) → refresh_token

   ↓ get_cards() → カード一覧
Select「💳 決済に使うカードを選択」
   ↓ card_id を保存

   ↓ 端末フィンガープリントを生成して固定（docs/04 §5.1）
✅ 登録完了（ephemeral）
```

- `jwtMfaToken` の有効期間は短いため、**1つ目の Modal 送信から続けて2つ目を開く**
- OTP を3回間違えたら中断し、最初からやり直させる
- 登録直後にヘルスチェックを1回実行し、失敗したら `DEGRADED` で登録する

### 6.2 `/kyash add`

```
Modal「🔑 Kyashアカウントを追加」
 ┌ 表示名（任意） ─────────┐
 ┌ メールアドレス ─────────┐
 ┌ パスワード ────────────┐

   ↓ Kyash(email, password) → SMS送信

Modal「🔑 認証コードの入力」
 ┌ SMSで届いた6桁 ────────┐

   ↓ login(otp)
   ↓ access_token / client_uuid / installation_uuid を暗号化保存
   ↓ get_profile() → is_kyc / get_wallet() → 残高
✅ 登録完了（ephemeral）
```

⚠️ `client_uuid` と `installation_uuid` は**2つで1セット**。
これを保存しておけば以後の再ログインで OTP が不要になる（`docs/03` §2.1）。**必ず両方保存すること。**

## 通信を使う新しい機能（2026-10 追加）

| 機能 | 設定コマンド | 既定 |
|---|---|---|
| できあがり通知 | `/config ready_notify <on/off> [分] [秒]` | **無効** |
| 近くの店舗 | 設定不要（索引に位置が入り次第きく） | 有効 |
| 入金の照合 | 設定不要（毎朝9時・管理者へ通知） | 有効 |
| 返金 | `/config refund <on/off> [上限]` → `/admin refund` | **無効** |
| 新商品・価格改定のお知らせ | `/config menu_news #チャンネル` | 無効 |

### できあがり通知
注文後しばらく相手の状態を見張り、できあがったら本人へDM。

⚠️ **相手の状態値の意味は分かっていない。** ブザー番号が出たらそれを合図に、
出なければ「注文時から状態値が変わった」ことを合図にしている。
見かけた状態値は監査ログ（`order.ready`）に残るので、
本当の意味が分かれば固定できる。

⚠️ 有効にすると通信が増える。1件の注文につき最大「見張る分数 ÷ 間隔」回。
同時に見張るのは `READY_MAX_WATCHED`（既定20）件まで。

### 近くの店舗
店舗索引を作るときに緯度経度も残すようにした（**通信は増えない**。
以前から取得していて捨てていたデータ）。注文できない店舗を選んだときに、
近くの対応店舗を3件出す。位置が無い店舗は出さない。

### 入金の照合
毎朝9時に、Kyash の入金履歴とこちらの記録を突き合わせる。

⚠️ **読むだけ。見つけても自動では直さない。**
お金の帳尻を機械が勝手に合わせるのが一番危ない。
履歴に受取IDが入っていないため、口座と金額でしか照らせない。

### 返金
⚠️ `/admin grant` の残高調整とは**別物**。実際に Kyash からお金が出る。

順番が要。**先に残高を引いてから**送金リンクを作る。
逆にすると、作れたのに引けなかったときに二重取りになる。
リンクを作れなかったら残高を戻す。

### 新商品・価格改定のお知らせ
管理者向け（店舗ごと）とは別に、利用者向けは**全店まとめて**出す。
同じ新商品が300店舗ぶん並んでも読めないため、商品名で束ねる。

## PayPay でのチャージ（2026-10 追加）

| コマンド | 内容 |
|---|---|
| `/paypay add` | 口座を登録（SMSで**URL**が届く） |
| `/paypay confirm` | 届いたURLを貼って確定 |
| `/paypay list` | 登録済み口座の一覧 |
| `/paypay methods` | Kyash / PayPay / 両方 を切り替え |
| `/paypay proxy` | PayPay用プロキシ（口座ごとの指定が優先） |

### なぜアプリ側のAPIを使うのか

PayPay には口が2つある。**必ずアプリ側を使うこと。**

| | Web側 `www.paypay.ne.jp` | **アプリ側 `app4.paypay.ne.jp`** |
|---|---|---|
| トークン寿命 | 2時間 | **90日** |
| 更新トークン | 無し | あり |
| 送金リンク作成 | **2024年3月に廃止（404）** | 使える |

解析元: https://github.com/taka-4602/PayPaython-mobile
（`PayPaython`（無印）はWeb側なので使わない）

### ログインの手順（**飛ばせない**）

相手は www.paypay.ne.jp 側で Cookie を積み上げながら進む作りになっている。
いきなり資格情報を送っても通らない。

```
① app4   /bff/v2/oauth2/par              要求を登録し requestUri をもらう
② portal /portal/api/v2/oauth2/authorize
③ portal /portal/oauth2/sign-in
④ portal /portal/api/v2/oauth2/par/check
⑤ portal /portal/api/v2/oauth2/sign-in/password   ← ここで初めて資格情報
```

⑤の応答に `redirectUrl` が入っていれば **端末が登録済み** で、
SMSなしでそのままトークンまで進める。入っていなければSMSでURLが届く。

⚠️ app4 側は「アプリ」、portal 側は「アプリ内ブラウザ」として
   振る舞う必要がある（ヘッダがまったく別）。

⚠️ `token_refresh` は README に書かれているが、**実物のコードには無い**
   （GitHub・PyPI 4.3.0 とも確認）。期限が切れたら登録し直す。

### ログインが2段階である理由
SMS で届くのは数字のOTPではなく **URL**。`/paypay add` で始めて、
届いたURLを `/paypay confirm` に貼る。`device_uuid` を保存してあるので、
次からはSMSなしで入り直せることがある。

⚠️ ログイン3回失敗でアカウントが一時ロック。
⚠️ **日本からしかアクセスできない。** 国外ならプロキシが必須。

### 記帳の順序（Kyash と同じ）
リンクを読む → 予約 → 受取前の残高 → **受け取り** → 残高の差分を検証 → 記帳。
差分が金額と合わなければ記帳せず、人の確認待ちにする。

## プロキシ（通信の出口）の設定（2026-10 追加）

BOT が外へ出る通信を、どの出口から出すかを決める。
マクドナルドと PayPay は**日本国内から**でないと使えないため、
国外のサーバーで動かす場合は日本のプロキシが必須になる。

### コマンド

| コマンド | 内容 |
|---|---|
| `/proxy show` | いまの設定と、その出どころを表示 |
| `/proxy set url:... [service:...]` | 設定する（直後に通るか確かめて結果を返す） |
| `/proxy clear [service:...]` | 解除する（解除後に何が効くかも表示） |
| `/proxy test` | 実際に通信して、**外から見えるIP**を一覧表示 |

⚠️ `/config` の下には入れていない。`/config` のサブコマンドが
   Discord の上限（25個）に達しているため、独立したコマンドにしてある。

⚠️ 応答はすべて ephemeral。プロキシのURLには認証情報が入るため、
   チャンネルに残してはいけない。

### 決め方の優先順位（上が強い）

| | どこ | 変え方 |
|---|---|---|
| ① | 口座ごとの指定 | `/mcd add` `/kyash add` `/paypay add` の `proxy` 引数 |
| ② | サービスごとの設定 | `/proxy set service:マクドナルド url:...` |
| ③ | 全体の設定 | `/proxy set url:...` |
| ④ | 環境変数 | `BOT_PROXY` |
| ⑤ | main.py の設定欄 | `PROXY_URL = "..."` |
| ⑥ | 指定なし | そのまま出る |

①を一番強くしてあるのは、口座ごとに出口を分けたいことがあるため
（同じIPから複数アカウントで入ると目立つ）。

### サービスの区分

`mcd` / `kyash` / `paypay` / `discord` / `web`
（`web` は注文番号ページへの push と、商品画像の取得）

### Discord 自身の接続

`commands.Bot(proxy=..., proxy_auth=...)` で通している。

⚠️ **Discord だけは `/proxy set` が即座には効かない。**
   ログインは DB を読む**前**に始まる（login → setup_hook → connect）ため、
   起動時点で読めるのは `main.py` の `PROXY_URL` と環境変数だけ。
   コマンドで変えた分は**次の起動から**反映される。画面にもそう出している。

⚠️ Discord（aiohttp）は認証情報を URL に入れた形を受け取らない。
   `core.proxy.split_auth()` で URL と `aiohttp.BasicAuth` に分けて渡す。

### 使える種類は http と https だけ

`core.proxy.SCHEMES = ("http", "https")`。socks は受け付けない。

⚠️ 理由は2つ。
   ① httpx で socks を使うには `socksio` を追加で入れる必要があり、
      入れずに socks の URL を渡すと **クライアントを作る時点で
      ImportError** になる。設定を1つ間違えるだけでBOTの通信が全部止まる。
   ② Discord への接続（aiohttp）は、そもそも socks に対応していない。
      許すと「他は通るのに Discord だけ通らない」という分かりにくい
      状態になる。

   追加の部品を入れずに、どこでも同じように動く形だけを残してある。

⚠️ 断る場所は2段ある。
   ・`/proxy set` … `problem()` が理由を日本語で返して設定させない
   ・`core.proxy._usable()` … `main.py` の `PROXY_URL` と環境変数は
     `problem()` を通らないため、ここで外して直接つなぐ。
     エラーログは**同じ値につき1回だけ**出す。

### 設定したら必ず確かめる

設定しただけでは効いているか分からない。
`/proxy set` は保存した直後に実際に通信し、`/proxy test` は
プロキシなし／各サービスを並べて、**相手側から見えるIP**を表示する。
「日本から出ているつもりで海外から出ていた」はこれでしか見つけられない。

### 使い回している接続

カタログ（店舗・メニュー）の取得は1本の接続を使い回しているため、
設定を変えても勝手には切り替わらない。
`core.http.catalog_client()` が設定を見張り、変わっていたら作り直す。

### 認証情報の扱い

⚠️ プロキシのURLにはパスワードが入る。**そのままの形で出してはいけない。**

* 画面・ログ … `core.proxy.mask()` を通す（`http://u:***@host:port`）
* 設定の保存 … `core.settings.SECRET_KEYS` に入れてあり、
  保存ログも監査ログも伏せた形でしか書かない
  （呼び出し側で `audit=False` を書く方式は書き忘れで漏れるため、
  保存処理の側で伏せている）

ホスト名までは残している。どこを通しているかは調べ物に要るため。

# サーバー管理（2026-10 追加）

チケット・認証・監視・処分の4つ。
注文BOTとしての機能とは独立していて、どれも**既定ではOFF**。

## 使う前に：2つのインテント

Discordの「特権インテント」が要るものがある。
**要らないものは要求しない**方針なので、使う機能に応じて設定する。

### SERVER MEMBERS INTENT（`main.py` の `SERVER_MANAGEMENT = True`）

入退室の記録・認証・レイド検知・メンバー数カウンターに要る。

### MESSAGE CONTENT INTENT（`main.py` の `MESSAGE_CONTENT = True`）

| 機能 | 要る？ |
|---|---|
| 入退室・ロール・BAN・VCの記録 | 要らない |
| メンション爆撃の検知 | **要らない**（Discordが内容とは別の項目で送ってくる） |
| 連投の速さの検知 | **要らない**（件数は内容を読まなくても数えられる） |
| チケットの書き起こし | **要らない**（履歴の取得はRESTなのでインテントの対象外） |
| 消された／編集されたメッセージの**内容** | **要る** |
| NGワード・招待リンクの検知 | **要る** |
| 同じ文の繰り返しの検知 | **要る** |

⚠️ 要るのに無い場合、各コマンドの応答と `/guard status` が
   「いまは効きません」と**はっきり言う**。黙って効かないのが一番困る。

## 1. チケット `/ticket`

| コマンド | 内容 |
|---|---|
| `/ticket setup` | 受け付けのON/OFF・方式・置き場所・担当ロール・控えの送り先 |
| `/ticket status` | いまの設定と件数、足りない権限 |
| `/ticket staff` | 担当ロールの追加・削除 |
| `/ticket rules` | 同時に開ける数・自動で閉じる時間・担当への声かけ |
| `/ticket kinds` | 相談の種別（最大25個） |
| `/ticket close` | 閉じる（開いた本人と担当者） |
| `/ticket add` / `remove` | 人を呼ぶ・外す（担当者） |

設置は `/panel ticket <チャンネル>`。

### 専用チャンネル方式（既定）とスレッド方式

⚠️ **担当者から見えるかどうかが違う。**

* チャンネル … ロールに閲覧権限を与えるだけで担当者全員に見える
* スレッド … ロールを@メンションしても**そのロールの人はスレッドに入らない**
  （Discordの仕様）。親チャンネルで担当ロールに
  「スレッドの管理」権限を与える必要がある

既定をチャンネルにしたのはこのため。`/ticket status` が
スレッド方式のときに毎回この注意を出す。

⚠️ チャンネルはサーバー全体で500個、1カテゴリ50個まで。
   残り5個で知らせ、0個なら利用者に「いっぱいです」と伝えて断る。

### 開くときに用件を聞く

種別を選ぶ → 件名と内容を書く画面が出る → 場所ができて内容が転記される。
空の場所を作って「ご用件は？」と聞き直すより1往復早く終わる。

### 書き起こし

閉じるときに `channel.history()` で取り、テキストにして控えの送り先へ送る。

⚠️ RESTでの取得なので **MESSAGE CONTENT INTENT は要らない**。
   「メッセージ履歴を読む」権限だけ要る。

⚠️ 記録に失敗しても閉じる処理は進める。閉じられないままだと、
   同時オープン数の上限に引っかかって次の問い合わせができなくなる。

スレッド方式は消さずに閉じる（あとから読み返せるように）。
チャンネル方式は消す。

### 放置の自動クローズ

`last_activity_at` を発言のたびに更新し、既定72時間で閉じる。

⚠️ 発言の記録は `on_message` で全メッセージを通るため、
   **チケットの場所のIDをメモリに持って先に弾く**（DBを引かない）。
   このメモは起動時に `reload_cache()` で作り直す。
   作り直さないと、再起動後に対応中のチケットが放置と見なされる。

## 2. 認証 `/verify`

| コマンド | 内容 |
|---|---|
| `/verify setup` | ON/OFF・付けるロール・やり方・未認証ロール・記録先 |
| `/verify rules` | アカウント年齢の条件・未認証の自動退出・失敗の上限 |
| `/verify status` | 設定と人数、足りない権限 |
| `/verify user` | 手動で認証する |
| `/verify reset` | 失敗回数を取り消す |
| `/verify bulk` | **すでにロールを持つ人を認証済みにする**（途中導入時） |

設置は `/panel verify <チャンネル>`。

### やり方

* **ボタン** … 押すだけ
* **画像認証** … 画像の文字を入力（Pillowで生成）

⚠️ 認証は「人かどうか」を見るものではない。ボタンは自動化すれば突破できる。
   それでも、使い捨てアカウントには手間がかかるので意味がある。
   強くしたいときは**アカウント年齢の条件**と併せて使う。

### 画像認証の作り

⚠️ 使う文字から **0 O 1 I 2 Z 5 S 8 B を外してある**。
   混ぜると、正しく読めた人を弾いてしまう。

⚠️ 傾き・ゆらぎは控えめ、線は細く。
   「機械に読ませない」より「人が読める」を優先する。

⚠️ 答えは**DBに置かない**（メモリのみ・5分で失効）。
   残すと「答えの一覧」という持ちたくないものになる。
   出題は `secrets` で作る（`random` では推測されうる）。

答え合わせは全角・半角・大文字小文字・空白の違いを許す。読めていれば通す。

### ロールを付ける順序

⚠️ **ロールを付けてから記録する。** 逆にすると、付けられなかったのに
   「認証済み」になって二度と押せなくなる。

BOTより上の位置にあるロールは付けられないので、先に見て日本語で断る。

### 未認証の自動退出

⚠️ **認証パネルが無いまま動かすと、入った人を順に追い出す。**
   そのためロール未設定なら何もしない。`/verify rules` でONにしたときは
   「パネルを設置してからお使いください」と必ず出す。

## 3. 監視 `/guard`

| コマンド | 内容 |
|---|---|
| `/guard setup` | 記録先・処分の記録先 |
| `/guard status` | 設定・足りないインテントと権限 |
| `/guard events` | 記録する出来事の切り替え（10種類） |
| `/guard raid` | 短時間の大量入室への備え |
| `/guard unlock` | 上げた認証レベルを戻す |
| `/guard spam` | 連投・メンション爆撃 |
| `/guard words` | NGワード・招待リンク |
| `/guard exempt` | 検知の対象から外すロール |
| `/guard counter` | メンバー数をチャンネル名に出す |
| `/guard recent` | 最近の検知 |

### 記録できる出来事

入室・退室・BAN・ロール変更・表示名変更・発言停止・
メッセージ削除・メッセージ編集・チャンネル作成削除・ボイス入退室

⚠️ **記録先チャンネル自身の出来事は記録しない。**
   記録先で「メッセージが消された」を記録すると、それがまた記録を生み、
   無限に増え続ける。`logs.is_log_channel()` で必ず弾く。

⚠️ 権限不足の警告は**チャンネルごとに1度だけ**。
   毎回出すと、15分ごとの同期ログに混ざって読めなくなる。

### 検知の作り

| 見るもの | 内容が要る？ | 既定 |
|---|---|---|
| メンションの数 | 要らない | 6個まで |
| 投稿の速さ | 要らない | OFF（5秒で6件） |
| 同じ文の繰り返し | 要る | OFF（3回続けて） |
| 招待リンク | 要る | 素通し |
| NGワード | 要る | なし |
| 短時間の大量入室 | — | OFF（10秒で5人） |
| 作りたてのアカウント | — | OFF |

⚠️ **自動で人を罰する機能なので、誤検知が一番の害になる。**
   疑わしいときは何もしない方を選ぶ。

⚠️ BOT・管理者・除外ロールは必ず対象外。
   外さないと、BOTの連続投稿をスパムとみなして自分を止めてしまう。

⚠️ 対処したときは必ず `GuardHit` に残す。
   消された人は理由を知れないので、説明できる形にしておく。

⚠️ 時刻は `time.monotonic()` を使う。壁時計だと時刻修正で数え間違える。

NGワードは全角半角・大文字小文字をそろえ、
**空白を抜いた形でも**見る（「あ い う」での逃げに備える）。
ただし抜いた形だけで見ると別の語がつながって誤検知するため、両方で見る。

### 荒らし（レイド）

既定は「知らせるだけ」。`lockdown` にすると
サーバーの認証レベルを「高」に上げる（`/guard unlock` で戻す）。

⚠️ 同じ波で何度も鳴らさないよう、検知したら数えをリセットする。

### メンバー数カウンター

⚠️ チャンネル名の変更は **10分に2回**まで（Discordの制限）。
   そのため更新は10分間隔（`server_upkeep` ループ）にしてある。

## 4. 処分 `/mod`

| コマンド | 内容 |
|---|---|
| `/mod warn` / `warnings` / `unwarn` | 警告・履歴・取り消し |
| `/mod warn_rules` | 警告がたまったときの自動処分 |
| `/mod timeout` / `untimeout` | 発言停止・解除 |
| `/mod kick` / `ban` / `unban` | 退出・BAN・解除 |
| `/mod purge` | 一括削除 |
| `/mod slowmode` / `lock` | 低速モード・封鎖 |

### 必ず守ること

⚠️ **処分は全部 `core/audit.py` に残る**（誰が・誰を・なぜ・いつ）。
   記録が無いと、あとから「不当だ」と言われて何も示せない。

⚠️ **本人への連絡は、キック・BANの前に送る。**
   あとだと共通のサーバーが無くなり、DMが届かなくなる。
   届かなかった場合は実行者にそう伝える（黙って成功と言わない）。

⚠️ 処分できない相手は、Discordに投げる前に日本語で断る
   （自分自身・BOT・サーバー所有者・BOTより上のロール・自分と同じ以上のロール）。
   投げると403が返るだけで、管理者には何が起きたか分からない。

### Discord の制限

* 発言停止は **28日**まで
* 一括削除は **14日より古いメッセージを消せない**
  → 指定より少なかったら、その理由を出す
* BANの `delete_message_seconds` は7日まで

### 自動処分

警告がたまったら発言停止 → キック → BAN。
⚠️ **強い方が勝つ**（5回でBAN・3回で停止なら、5回目はBAN）。

### 封鎖

⚠️ `@everyone` の「メッセージを送信」**だけ**を変える。
   他の権限は触らない（戻すときに元の設定を壊さないため）。

# 利用を広げる機能（2026-10 追加）

## 1. 声かけ `/growth nudge`

あと一歩で使える人に、DMで**1回だけ**声をかける。

| 種類 | いつ | 持ち出し |
|---|---|---|
| ようこそ案内 | 認証が済んだとき（認証OFFなら入室時） | 増えない |
| カートの残り | カートを残して8分（既定） | 増えない |
| チャージ後の未注文 | チャージから6時間、注文が無い（既定） | 増えない |
| 残高のお知らせ | 残高があるのに14日注文が無い（既定） | **増えない** |

⚠️ **この機能の一番の失敗は「送りすぎ」。**
   しつこいDMは、使ってもらえないどころかサーバーごと抜けられる。
   歯止めを3つ、必ず通す。

| | 仕組み |
|---|---|
| ① 利用者が止められる | `User.nudge_notify`。DMのボタン1つで切れる |
| ② 同じことは二度言わない | `Nudge` 表の一意制約 `(discord_id, kind, key)` |
| ③ 一度に送りすぎない | `NUDGE_BATCH = 20`（種類ごと） |

### 鍵（key）の決め方

「どの出来事に対する声かけか」を表す。ここが同じなら二度目は送らない。

| 種類 | 鍵 | 意味 |
|---|---|---|
| welcome | `"once"` | 一生に1回。入り直しても送らない |
| cart_left | カートの更新時刻 | カートを組み直せば、また声をかけられる |
| charged_unused | 入金の記録ID | チャージごとに1回 |
| idle_balance | `b{何回目の期間か}` | 30日ごとに1回（毎日言わない） |

### 必ず守ること

⚠️ **記録を先に書いてから送る。** 送ってから書くと、送信の途中で
   落ちたときに同じ人へ何度も送ってしまう。

⚠️ 届かなかったことも記録する（`Nudge.delivered = False`）。
   DMを閉じている人を毎回むだに試さないため。

⚠️ カートの声かけは、カートの有効時間（`CART_RESUME_MINUTES = 15分`）
   より**短い**時刻に設定すること。消えたあとに「続きからどうぞ」と
   言っても続きが無い。`/growth nudge` は長すぎる設定に警告を出す。

⚠️ ようこそ案内は、認証を使っているなら**認証が済んだとき**に送る。
   入室直後だとまだ中が見えていないので読まれない。
   二重に送らないよう、入室時の送信は認証OFFのときだけにしてある。

### 誰に送るかの絞り込み

⚠️ **利用者全員に1件ずつ問い合わせない。** 人数×2のクエリが10分おきに
   走ることになる。最後の注文はSQLでまとめ、残高は
   `core.ledger.user_balances()`（GROUP BY 1回）で引く。
   1,500人でもSQLは5回で済む（`tests/test_scale.py` で固定）。

## 2. 再注文

注文履歴の下に「同じ内容でもう一度」が出る。選ぶとカートを組み直す。

⚠️ **中身をそのまま信じない。** 前の注文から時間が経っていると
   終売・時間帯外・価格改定が起きている。
   `open_menu(resume=..., reorder=True)` に渡して、
   **取り直したメニューで作り直す**。この面倒を見る場所を1つにまとめ、
   続きから（resume）と同じ処理を通す。分けると片方を直し忘れる。

⚠️ 成立した注文だけを出す（COMPLETED / NOTIFIED / CAPTURED）。
   失敗した注文を「もう一度」と誘うのは、同じ失敗を繰り返させること。

⚠️ 他人の注文を開けないよう、`Order.discord_id` を必ず確かめる。

⚠️ 全部が終売だったときに「ご用意しました」と出さない。カートは空なので、
   そう伝える。

## 3. 時間帯に合わせた提案

朝マック・ヒルマック・夜マックなど、**いまだけ頼めるもの**を知らせる。

* カート画面に「いまの時間帯」を出す
* カテゴリ一覧で、その時間帯のものを**先頭**に出し `⏰` を付ける

⚠️ 「レギュラー」は伝えない（`NOTABLE_DAYPARTS`）。一日の大半なので、
   知らせても選ぶ助けにならず、本当に伝えたい朝マック・夜マックが埋もれる。

⚠️ 時刻を決め打ちしない（朝マックは5:00〜、など）。店舗ごとに違うので、
   保存してある実際の営業データ（`StoreDaypart`）から判定する。

⚠️ 注文パネル（常設）には出さない。貼り直しが manual なので、
   時間が経つと嘘になる。**店舗が決まってから**出す。

## 4. 紹介ランキング `/panel ranking`

今月に成立した紹介の数で並べた、ボタンの無い常設パネル。

⚠️ 基準は `qualified_at`（条件を満たした時刻）。招待した時刻ではない。
   先月に招待して今月に成立した分は**今月**に数える（特典が出たのが今月だから）。

⚠️ 月の区切りは日本時間（`config.jst_month_start_utc()`）。
   UTCで切ると、毎月1日の朝9時までが前月に入る。

# この回に見つけて直した、既存機能のバグ

## ① 匿名コードの衝突で、一部の人がBOTを使えなくなる（重大）

`User.anon_code` は sha256 の頭**4桁**（65,536通り）だった。
誕生日問題により

| 人数 | 衝突している確率 |
|---|---|
| 100人 | 7% |
| 300人 | **50%** |
| 1000人 | ほぼ確実 |

衝突すると `anon_code` の一意制約で **`ensure_user()` が失敗**し、
その人は行そのものが作れない。つまりチャージも注文も一切できない。
原因も表に出ないため、まず気づけない。

**直し方**
* 桁数を 4 → **6**（16,777,216通り）に伸ばした
  （既存の人は保存済みの値をそのまま使うので、コードは変わらない）
* それでも衝突したら、`_free_code()` が 8 → 10 → 12 桁と伸ばして逃がす
  （同じ人には必ず同じ値。匿名コードの存在理由が「同じ人と分かること」なので）

3,000人を実際に登録して全員ぶん重複が無いことを確認（`tests/test_scale.py`）。

## ② 招待コードも同じ形だった

`invite_code` は 8.9億通りなので危険度はずっと低い（5,000人で1.4%）が、
衝突すると招待コードを受け取れなくなる作りは同じだった。
`code_for(id, salt=n)` を足し、ぶつかったら塩を変えて逃がす。

⚠️ 返す値を「導いた値」から「**実際に保存した値**」に変えた。
   食い違ったままだと、画面に出すコードを貼っても誰も引けない。

⚠️ すでにコードを持っている人は変えない。配ったあとに変えると、
   出回っているリンクが死ぬ。

## ③ `/panel refresh` がチケット・認証パネルを更新していなかった

`refresh_all()` の `builders` にこの2つが入っておらず、
しかも「チャンネルが見つかりません」という**原因と違う**メッセージが
出ていた。両方を直し、「知らない種類」と「チャンネルが無い」を
別のメッセージにした。設置できるパネルが全部更新できることを
テストで固定した（`tests/test_growth.py`）。

# セットが注文できなかった原因（2026-10-05 解決）

## 症状

セット系の商品で、ドリンクなどを選んだ瞬間に
**「BOTは時間内に応答しませんでした」** と出て先へ進めない。

## 原因：確定ボタンの行を決め打ちしていた

`OptionView._build()` が、確定ボタンを **`row=3` 固定**で置いていた。

```python
ok = discord.ui.Button(..., row=3)   # ← これ
```

一方で選択枠（Select）は `row` 0〜3 の4行まで使う。
枠が4つある商品では **row 3 に Select がすでに居る**ため、
そこへ Button を足そうとして

```
ValueError: item would not fit at row 3 (6 > 5 width)
```

で**ビューを作る処理ごと落ちていた**。

⚠️ 落ちると応答を返せないので、Discord は3秒で打ち切る。
   利用者には「BOTは時間内に応答しませんでした」としか見えず、
   何が悪いのか分からない。

## Discord の行の決まり

| | |
|---|---|
| 1画面 | 5行（row 0〜4） |
| Select | 1つで**1行を丸ごと**使う（幅5） |
| Button | 幅1。1行に5個まで |

つまり **Select がある行に Button は置けない**。

## 影響した商品：42件

| 落ち方 | 商品 |
|---|---|
| 開いた瞬間に落ちる（枠が4つ） | ハッピーセット5種 |
| **選んだあとに**落ちる | その他のセット37種（ビッグマック、月見、ひるまック、倍シリーズなど） |

⚠️ 後者が厄介だった。開いた時点では枠が3つで収まっているが、
   ドリンクを選ぶと**サイズの選択が増えて4行目まで埋まり**、
   作り直しのときに初めて落ちる。
   「開けるのに、選ぶと死ぬ」ため、画面を開くだけの確認では見つからない。

## 直し方

ボタンは**選択枠を置いた次の行**に置く。

```python
btn_row = min(row, 4)      # row は Select を置き終えた時点の次の行
```

ハッピーセットの場合：選択枠が row 0〜3、ボタンが row 4 で、ちょうど5行。

## 再発を防ぐ検査：`tests/test_views.py`

⚠️ この種の不具合は、**既存のテストでは絶対に見つからない**。
   注文の組み立て（protobuf）も、枠の候補の抽出も、全部正しかった。
   壊れていたのは「画面を組み立てられるか」だけだった。

そのため、**全商品 × 全画面**を実際に構築する検査を足した。

* 選択枠の画面を、朝・昼・夜の3つの時間帯すべてで作る（477通り）
* **選んだあとの作り直しも試す**（後者の落ち方を捕まえるため）
* どの行も幅5を超えないこと
* ボタンと選択枠が同じ行に無いこと
* 商品詳細・具材の調整・カテゴリ一覧・商品一覧も全部作る
* 1画面25部品、選択肢25個の上限

## 調べ方：`/debug fails`

失敗した注文について「送った中身の木」と「マクドナルドの応答」を
並べて出す。どちらか片方だけでは原因が分からない。

今回はログに例外がそのまま出ていたため、これを使う前に解決した。

# セットのドリンクで注文が断られる問題（2026-10-05 解決）

## 症状

セットを注文すると
「ただいまのお時間は選択した商品のお取り扱いがありません」で失敗する。

## 相手は原因を教えてくれていた

応答の中身にこう入っていた。

```
9030 > 9997925 > 3120 product not found
└セット  └ドリンク枠  └コカ・コーラ M
```

**マクドナルドは「どの枠に、どの商品を入れたのが駄目か」を正確に
教えてくれている。**

## 原因①：その経路を読んでいなかった

`learn_rejected_choices()` は応答を読まず、注文全体から
疑わしいものを**絞り込んで推測**していた。

⚠️ 疑いが2つ以上あると「巻き添えを避けるため」何も覚えない作りだった。
   セットには枠が3つ以上あるので、ほぼ常に2つ以上疑わしい。
   つまり **実質的に一度も学習できず**、同じ組み合わせで
   何度でも失敗し続けていた。

**直し方**：`errors.rejected_pairs()` で経路を読み、
相手が指した組み合わせだけを正確に覚える。推測は、経路が
入っていなかった場合の保険として残した。

## 原因②：断られた商品を、候補の先頭に押し戻していた

`choice_candidates()` は代表商品（`referenceProduct`）を
「マクドナルド側が代表として指定しているものなので」という理由で
**無条件に先頭へ戻して**いた。

⚠️ 枠 9997925 の代表はまさに **コカ・コーラ M**。
   つまり断られた商品が、学習しても候補の**1番目**に出続け、
   上から選んだ人が必ず失敗していた。

**直し方**：断られた記録があるものは戻さない。

⚠️ ただし**候補が0件になるのはもっと悪い**（枠を埋められず、
   その商品を一切注文できなくなる）。全部断られた場合だけは、
   代表を戻して望みをつなぐ。

## 結果

1回の失敗で、その組み合わせだけが正確に候補から外れる。
他のドリンクは巻き添えにならない。

# `/debug fails` を実際に使える形にする（2026-10-06）

## ⚠️ 原因不明の注文でだけ落ちていた

商品名を引く道具 `nm()` を `try` の**中**で作っていた。

```python
try:
    dec = decode_hex(o.hex_payload)
    def nm(code): ...        # ← ここで作っていた
except ProtocolError:
    ...
# この下で nm() を呼ぶ → UnboundLocalError
```

注文コードが読めないと `nm` が未定義になり `UnboundLocalError` で落ちる。

**原因が分からない注文ほど中身が読めない。**
つまり**一番必要な場面でだけ**窓口が使えなくなっていた。

直し方：`nm()` は `try` の外で作る。

テストは文面を眺めるのではなく、**壊れた注文を入れて実際に呼ぶ**。
文面の検査では「`try` の外に書いてあるか」しか見られず、
別の形で同じ失敗をしたときに気づけない。

## 応答の全文を添付する

画面には 700 文字しか出していなかった。**切れた先に原因が書いてある**
ことがあるため、切れた場合は `fails.txt` に全文を付ける。

付けるのは、応答・送った注文コード・送った中身（JSON）。
⚠️ `order_token` は入れない。調査に使わないものを渡す理由がない。

## ⚠️ 人に渡す前に認証情報を伏せる

この添付は**管理者が他人に貼るためのもの**。応答の本文に認証情報が
入ることは普通ないが、「普通ない」で漏らすと取り返しがつかない。

`errors.scrub()` が、鍵の名前（token, password, authorization 等）の
後ろにある8文字以上の値と、単体の JWT を伏せる。

```
"token":"abcd…（伏せました:19文字）"
Authorization: Bearer eyJ…（伏せました:JWT）
```

⚠️ **伏せすぎて原因が読めなくなっては意味がない。**
   商品コードと経路（`9030 > 9997925 > 3120`）は数字なので、
   鍵の名前の後ろにある長い文字列だけを狙う。
   伏せた後でも `rejected_pairs()` が経路を読めることをテストで固定した。

⚠️ 全部消さずに頭4文字と長さを残す。全部消すと
   「入っていた」ことまで分からなくなり、漏れていた事実に気づけない。

# 鍵が合わないとき（2026-10-07）

⚠️ これは起こりうる。バックアップを `data/encryption_key.txt` 無しで
   戻した場合、`ENCRYPTION_KEY` を書き換えた場合、鍵を作り直した場合。
   バックアップの案内文自身が「鍵も必要です」と言っている状況。

`core/crypto.py` に2つ足した。

| | |
|---|---|
| `try_decrypt(blob)` | 読めなければ `None`。例外を出さない |
| `is_unreadable(blob)` | 中身はあるのに今の鍵で読めないか |

⚠️ 中身が空のときと、読めなかったときは**違う**。`try_decrypt` は
   どちらも `None` を返すので、区別が要る場面は `is_unreadable` を使う。

| 場所 | 鍵が合わないときの振る舞い |
|---|---|
| `/kyash relogin` | 何が起きたか説明して止まる（鍵を戻すか登録し直す案内） |
| 注文（`_load_tokens`） | 落ちずに空として扱う。記録に残す |
| チャージ（`build_client`） | 落ちずに空のトークンにする |

⚠️ 注文の途中で例外にすると、利用者には理由の分からない失敗になる。
   「使えないアカウント」として普通の経路に乗せるほうがよい。

# アカウントまわりの改善（2026-10-10）

## ⚠️ 同時注文でアカウントが取り合いになっていた

```
同時に3件 → 選ばれたアカウント [1, 2, 1]   1番に2件、3番は未使用
順番に3件 → 選ばれたアカウント [3, 2, 1]   正しく分散
```

`pick_account()` は `last_used_at` で分散していたが、**同時に呼ばれると
3件とも書き込み前の値を読む**ため、同じアカウントを選んでいた。
`ORDER_CONCURRENCY = 3` なので常に起きうる。

害は2つ。

| | |
|---|---|
| 同時注文 | 実質1〜2アカウントしか使わず、並列になっていない |
| アカウント | 1つに注文が集中し、**機械的な使い方に見える** |

直し方：選ぶところを1件ずつ通し（`_pick_lock`）、選んだ直後に
「使用中」の印を付ける。印は `AccountHandle.aclose()` で外す。

⚠️ 全部ふさがっていても**例外にしない**。混んでいる時間に注文が
   丸ごと失敗するほうが悪い。使い回す（同時数は `core/queue.py` で
   既に絞ってある）。

⚠️ **閉じ忘れると、そのアカウントは二度と選ばれなくなる。**
   これは直そうとしたバグより悪い。呼び出し元7か所すべてが
   `finally` で閉じていることを確認したうえで、人の手に頼らないよう
   印に時刻を持たせ、15分を超えたら自動で外して警告を出す。
   テストは**構文木で全呼び出し元を数える**（同じ誤りは1か所とは限らない）。

## エラー分類のバグ2件

### ⚠️ 401 がすべて「決済の問題」になっていた

`PAYMENT` の判定語に裸の `"authoriz"` があり、これは
**`"unauthorized"` に含まれる**。`PAYMENT` は `AUTH` より先に
判定されるため、ログインが切れた401がすべて決済の問題になっていた。

管理者はカードを疑い、本当の原因に辿り着けない。
`"payment authoriz"` / `"authorisation fail"` に置き換えた。

### ⚠️ 複数語の判定語が一度も効いていなかった

`parse()` は `extract_strings()` が返す**単語**だけを突き合わせていた。

```
"product not found"  →  "found product"  →  一致しない
```

`product not found` / `card not found` / `invalid card` / `store closed`
がすべて死んでおり、**セット注文の失敗が UNKNOWN になっていた正体**。
利用者には「原因を特定できませんでした」としか出ていなかった。

生の本文も突き合わせに混ぜて直した。12通りの分類を検査で固定。

## `/mcd history <ID>` — 止まった理由の履歴

⚠️ `last_error` は**最後の1件しか残らない**。止まった理由は止まった
   **後**に調べるものなので、そのときには上書きされている。

失敗・降格・隔離・**復帰**を `McdAccountEvent` に残す。

⚠️ 分類は**目安**。判断の根拠は `raw`（生の応答）に置く。どんな
   止まり方をするかは実際に起きるまで分からない。分類できなくても
   `UNKNOWN` のまま残し、捨てない。

⚠️ 生の応答には認証情報が混ざりうる。`errors.scrub()` を通す。

⚠️ 記録のために処理を止めない。ここで落ちると注文そのものが失敗する。

## カードまわり

⚠️ **カード番号は扱わない。** 公式のRPC 29個すべてを確認したが、
   カードを登録する呼び出しは存在しない。`CheckIfThreeDSRequired` が
   あることから、3-Dセキュア（銀行の本人確認）を通す別画面で登録する
   作りになっている。こちらが受け取るのはカードの識別子だけ。

⚠️ **カードが無いアカウントは注文に選ばれない**（`pick_account` が外す）。
   気づかないと、使えるアカウントが静かに減っていく。

| | |
|---|---|
| 登録直後 | カードを見に行き、**1枚だけなら自動で設定** |
| `/mcd cards` | 全アカウントの状況。欠けているものを出す |
| 「カードを探す」 | 公式アプリで登録した後に押すと、まとめて検出 |

⚠️ **2枚以上なら自動で決めない。** どれで決済するかはお金の話で、
   勝手に選んでよいものではない。

⚠️ **すでに設定済みなら触らない。** 取り直すたびに上書きすると、
   せっかく選んだものが消える。

## `/mcd bulk` — 自分のアカウントをまとめて登録

⚠️ **新しくアカウントを作るものではない。** すでにマクドナルドに
   登録してあるアカウントを、このBOTへ取り込むだけ。

⚠️ 認証コードを求められたものは、ここでは進められない。コードは本人が
   受け取るものなので、まとめ処理の中で待てない。その分は `/mcd add`
   で1件ずつ案内する。

⚠️ 区切り文字を決め打ちしない（カンマ・コロン・タブ・スペース）。
   パスワードに区切り文字が入ることがあるので**最初の1つだけ**で切る。

⚠️ メールアドレスは画面にそのまま出さない（`ta***@example.com`）。
